## 一、改了什么

### 1. 契约 0.3.3

| 项 | 内容 |
| --- | --- |
| 新契约 `heartbeat_ack` | 心跳 200 响应原来只在 openapi 里内联定义，现在纳入契约：`schemas/heartbeat_ack.json`、模型 `HeartbeatAck` / `HeartbeatAccountBinding`、`validate_heartbeat_ack`、`check("heartbeat_ack", …)`。字段：`server_time`、`paused`、`policy_version`（≥1 或 null）、`cancellations[]`、`account_confirmed`（可省略）、**`account_binding`（必有，可为 null）** |
| `account_binding` | `{account_id, bound_at, confirmed_by}`，是服务端记录的、经控制台确认的绑定，**与心跳里报的 account_id 无关地如实返回**；没有确认的绑定为 null；绑定变更后返回新账户。字段与本机 `MonitorState.account_binding`（Protocol `AccountBinding`）完全一致，D2d 可直接写入 |
| 模型层规则 | `account_confirmed=true` 时 `account_binding` 不能为 null；`account_binding` 为 null 时 `policy_version` 必须为 null |
| `client_state` 增加 `suspended` | 协调者追加（D2c 接口请求 1）：本机模式窗口已归还用户或接管失败、GUI 挂起。导出 `ClientState`、`CLIENT_STATES`。服务端如实记录；设备卡片 `status` 仍为 online，控制台读 `last_heartbeat.client_state` |
| openapi | `components.schemas.HeartbeatAck` 改为 `$ref: ./schemas/heartbeat_ack.json`；postHeartbeat 与 confirmAccountBinding 写明"设备以心跳回执中的绑定为准"、变更绑定期间 `account_confirmed=false`、领取为空；Device.status 说明 suspended 时仍为 online |
| 文档 | contracts.md（产物表向量数、契约名列表、第七节 heartbeat_ack 与 client_state、账户来源、缺口裁决两行、变更记录 0.3.3）；api.md（3.1 第 4、5 步：设备以心跳回执中的绑定为准、变更 / null / 旧服务端三种情形；3.2 回执字段与 suspended；第一节令牌配置） |
| 向量 | 合法 +4（heartbeat_ack_unbound / bound / binding_not_yet_local、device_heartbeat_suspended），非法 +3（confirmed_without_binding、binding_missing_confirmed_by、missing_binding）；现为合法 50、非法 71 |

兼容性：0.3.x 互相兼容。旧客户端忽略新字段；新客户端遇到没有 `account_binding` 的旧服务端时应保持本机绑定不变（api.md 3.1 已写）。**注意**：旧服务端会以 422 拒绝 `client_state=suspended`，客户端改报 suspended 必须在服务端升级到 0.3.3 之后上线。

### 2. 服务端心跳（M-1 服务端部分）

`DeviceService.heartbeat` 在响应里填 `account_binding`（来自 `account_bindings` 表，未绑定为 null），其余字段不变；路由 `response_model` 改为契约引用 `HeartbeatAckJson`（openapi 一致性测试按引用比较，通过）。

### 3. 服务端入口配置（M-4）

新增 `server/app/serve.py`，`python -m app.main serve` 转到这里：

- 控制台 / 服务令牌来源：环境变量 `MONITOR_CONSOLE_TOKENS` / `MONITOR_SERVICE_TOKENS`（`令牌=操作者`，逗号分隔，与原 `scripts/serve.py` 相同）、令牌文件 `--console-tokens-file` / `--service-tokens-file`（每行一个，`#` 注释，适合 0600 文件或 secret 挂载）、命令行 `--console-token` / `--service-token`（可重复；会出现在 `ps` 里，帮助文本写明仅调试用）。多个来源合并，同一令牌对应不同操作者、或同一令牌既是控制台又是服务令牌时拒绝启动。
- 校验：令牌至少 16 个字符；操作者名不超过 128（它会写进 `confirmed_by`，与契约上限一致）；没有控制台令牌时退出码 2，提示 `MONITOR_CONSOLE_TOKENS`。
- 令牌不进日志：报错、`ServeConfig.__repr__`、启动摘要行（`monitor-server 控制台令牌 N 个（操作者…）…`）都只有操作者名与个数。
- 顺带补上 M 报告提到的 Webhook 注入：`MONITOR_WEBHOOK_URL`、`MONITOR_WEBHOOK_SECRET` → `WebhookNotifier`。
- `--host`、`--port`（0 由系统分配）、`--db`；uvicorn 启动完成（含 lifespan 后台推进）后 stderr 打印 `monitor-server ready <url>`，与原脚本一致。
- `scripts/serve.py` 改为转调 `app.serve.main`（保留 `--db` 必填与原用法），integration 的真实进程冒烟（`test_real_server_process.py`，未改）照常通过。

## 三、决定与理由（协调者可推翻）

1. **单独的 `heartbeat_ack` 契约**，而不是只改 openapi 内联：任务要求"schema、模型"同步，客户端（D2d）也需要可校验的模型；做法与 policy 一致（openapi 直接 `$ref`）。
2. **`account_binding` 必有可空**：区分"服务端说没有绑定（null）"与"旧服务端没给（缺字段）"，后者客户端保持本机不变。
3. **字段名用 `account_binding`（任务书），没有用 M 报告建议的 `bound_account_id`**；三个字段与本机绑定一致，不含 device_id（与控制台 `AccountBinding` 响应不同，那个多一个 device_id）。
4. **v1 没有解绑接口**，本任务没有新增（不在范围）；"解绑如实反映"体现为：服务端没有绑定记录即 null，文档写明以后增加解绑也用 null 表达。
5. **suspended 不新增 Device.status 值**：进程在线就是 online，挂起由 `last_heartbeat.client_state` 体现，避免改 `Device.status` 枚举影响 I1/I2；如需单独状态请另行裁决。
6. **令牌最短 16 字符**：防止部署时用弱口令；integration 的 `smoke-console-token`（19）不受影响。
