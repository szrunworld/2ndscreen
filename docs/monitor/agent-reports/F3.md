## 实现概要

### 1. 搜索（`search.py`）

- `POST /search-runs`（控制台）：门槛依次检查策略存在且白名单包含 `search_candidates`、策略 `paused`、账户下已绑定设备是否全部暂停、每日上限、最小间隔。不满足时返回 409 `policy_blocked`，`errors[].code` 给出具体原因：`action_not_allowed` / `paused` / `device_paused` / `daily_limit_reached` / `rate_limited`。
  - 上限与间隔只能比 Monitor 本地更严：有效上限 = min(策略, 40)，有效间隔 = max(策略, 30 秒)。数值抄自 `client/monitor/core/limits.py`，server 不能 import client。
  - "今天"按策略 `work_hours.timezone` 划分。
  - 通过后创建 `search_candidates` 指令（`workflow_id=null`，`target={scope: current_page}`），`ttl_seconds` 默认 600。
- 快照：订阅 `CommandResultRecorded`，取 `output.snapshot` 原样存储（`fields`、`masked_name`、`prop_card_texts`）。`search_id` 与任务不符时不存。
- `outcome` 只由 coverage 得出：complete/partial → `results`，empty_confirmed → `no_results`，unreadable → `unreadable`。指令失败且没有快照时为 null。unreadable 的 status 是 `failed`，和 no_results（`completed`）分开。
- `status` 跟随指令：pending → pending，claimed/acked → running，succeeded → completed，failed/unknown/skipped → failed，另有 expired、cancelled。pending 且已过期的显示 expired。
- 搜索结果不能作为问候目标：契约已拒绝会话目标里的 `result_ref`，有测试锁定；本模块也不提供从结果发起动作的入口。

### 2. 登录接力（`login_relay.py`）

- `POST /login-qr`（设备令牌）：
  - 本机模式返回 403 `local_mode`，请求体 device_id 与令牌不符返回 403 `device_mismatch`，契约校验失败返回 422。
  - 每台设备只保留一张码：`qr_seq` 不小于当前值时覆盖（同时清除撤下标记），更小的视为迟到的旧码，忽略并返回当前生效的 seq。
- `GET /devices/{id}/login-qr`（控制台）：
  - 返回 200 时带 `Cache-Control: no-store`，每次读取都记录查看者。
  - 过期返回 410 `qr_expired`，同时删除内容；撤下返回 410 `qr_withdrawn`；从未上传返回 404。410 不记查看记录。
- `POST /devices/{id}/login-qr:withdraw`（设备令牌或控制台）：
  - 返回 204，撤下时删除内容，重复调用同样 204。
  - 设备令牌撤其他设备的码返回 403。
  - 撤下本身幂等，所以不保存首次响应；Idempotency-Key 只校验格式。
- `GET /devices/{id}/login-qr/views`：按时间顺序返回查看记录。
- 收到 `login_ok` 事件时自动撤下（`withdrawn_by=event:login_ok`）。设备卡片的 `login_qr_active` 默认接到 `LoginRelayService.is_active`。
- 人工输入：
  - 收到 `human_input_required` 事件时登记请求。同一 `input_request_id` 只登记一次，有效期 10 分钟（`INPUT_REQUEST_TTL`）。
  - `POST /input-requests/{id}/response` 只接受 can_fill=true、未回应、未过期的请求，否则分别返回 409 `input_not_fillable` / `input_already_responded` / `input_request_expired`；请求不存在返回 404。
  - 账户取事件的 account_id，为空时取设备绑定；两者都没有返回 409 `account_unbound`。
  - 生成的 `provide_input` 指令定向给发出请求的设备。
- 值不进日志与事件：
  - 响应里的 `payload.value` 打码为 `******`。
  - 指令有结果后，服务端立即把库里的值抹掉；`scrub_finished_inputs()` 处理已过期或已取消的指令。
  - 幂等记录只存进程内随机密钥做的 HMAC。明文哈希不行：6 位验证码可被穷举。
  - 有测试检查日志、事件表和 `GET /commands/{id}` 都不含该值。

### 3. 通知（`notify.py`）

- 接口 `Notifier`（`channel` + `send(notification)`）。两个实现：
  - `ConsoleTodoNotifier`：`notifications` 表，提供 `list_open` / `list_all` / `resolve`。
  - `WebhookNotifier`：POST JSON，可选 `X-Monitor-Signature: sha256=<HMAC>`，带 `X-Monitor-Notification-Id`；立即重试到 `max_attempts`，不 sleep。发送函数可注入，默认用标准库 urllib，不增加运行时依赖。
- `NotificationService` 订阅事件总线：

  | 来源 | 通知 kind |
  | --- | --- |
  | `login_required` 事件 | `login_required` |
  | `blocked_by_dialog` 事件 | `blocked_by_dialog` |
  | `login_qr` 事件 | `login_qr` |
  | 邮件记录进入 failed | `mail_failed` |
  | 核对结果为 issues_found / failed | `mail_verification` |
  | `CaseNeedsHuman` 消息（供流程模块发布） | `case_needs_human` |

- `notification_id` 由来源确定，同一来源只通知一次。
- 单个适配器失败只写 `notification_deliveries`，不影响其他适配器，也不影响触发它的 HTTP 请求。
- 通知正文不含候选人姓名、二维码内容和人工输入的值。
- `create_app(notifiers=[...])` 可以注入额外适配器；控制台待办总是启用。

### 4. 邮件记录与简历文档（`mail_endpoints.py`、`resume_documents.py`）

- `PUT /mail-messages/{id}`（serviceToken）：契约校验，并检查路径 = 请求体 = `compute_mail_message_id(provider_message_id)`。
  - 首次写入返回 201，之后返回 200；同状态写入是更新。
  - 先判 `MAIL_TRANSITIONS`（409 `illegal_mail_transition`），再判不可变字段和 sha256（409 `mail_message_conflict`），两种 409 都带 `existing`。
  - 比较时间时按时刻比较，邮箱不区分大小写。
  - 首次写入时不限制初始状态。
- `GET /mail-messages`：控制台或 serviceToken；status 可重复，可按 mailbox、message_id、received_after/before 过滤；按 received_at 倒序；游标是偏移量。
- `POST /mail-verifications`（serviceToken）：按 verification_id 幂等，同内容返回 200 和首次的 received_at，不同内容返回 409 `verification_conflict`。`GET` 按 finished_at 倒序，可按 mailbox、outcome 过滤。
- `POST /resume-documents`（serviceToken）：
  - **原件**
    - mail_message 必须已登记，否则 404。按 (mail_message_id, sha256) 去重，重复返回 200 和 `duplicate=true`；数据库也有部分唯一索引兜底并发。
    - `link.method` 规则：非 none 必须带 case_id，且流程存在（422 `unknown_case`）；resume_request 必须带 command_id，且它是该流程已成功的 request_resume（422 `link_command_invalid`）；其他方法不能带 command_id；none 时 case_id 必须为 null，文档进人工关联队列（`needs_manual`），`candidate_case_ids` 保存在 `link_json`。
    - 同一流程的原件按 version 递增保留，不覆盖。
  - **品牌化版本**：必须带 derived_from，不能带 mail 和 link（显式 null 也不行）。流程、mail_message_id、version 继承原件，按 (derived_from, sha256) 去重；只能从原件派生。
- `POST /resume-documents/{id}/parse-result`（serviceToken）、`GET` 列表（控制台或 serviceToken）与详情。
- `POST /resume-documents/{id}:link`（控制台）：
  - 记录 `manual_action(link_resume)`，含 actor、时间、note；原始的 `link_json` 不覆盖；派生的品牌化版本跟着关联。
  - 已关联到其他流程返回 409 `already_linked`；已关联到同一流程只补记人工处理；对品牌化版本调用返回 409 `not_original`。
  - 来源邮件处于 needs_review 且它的原件都已关联时，推进为 processed。

## 已知限制

- 搜索的每日上限按"当天创建的搜索任务数"计，没有扣除已取消或过期的任务，比 F2 的口径（不计没有结果的已取消/过期指令）更严。
- 列表分页：mail-messages 和 mail-verifications 按时间倒序，用偏移量游标，翻页期间有新记录插入时可能重复或漏读一条；其他列表沿用 F1 的 seq 游标。
- `scrub_finished_inputs()` 和 `LoginRelayStore.purge_expired()` 没有定时调用。二维码在读取时顺手清理，值在指令有结果时立即抹掉；过期或取消的指令要靠定时任务，可挂到 F2 的后台 tick 上。
- `scrub_command_value` 直接改 F1 的 `commands.command_json`（只改 provide_input 的 `payload.value`），没有改 `db.py` / `commands.py` 的代码。
- `WebhookNotifier` 立即重试，不退避；投递失败只记录，不补发。待办列表里仍然能看到。
- 进程内的 HMAC 密钥重启后会变：重启后同一个 Idempotency-Key 重放人工输入会得到 422（控制台每次点击都生成新键，实际不受影响）。
