## 五、设计要点

1. **事务**：连接用 `isolation_level=None`，每个公开方法在 `_tx()` 里执行；写方法 `BEGIN IMMEDIATE`，读方法 `BEGIN DEFERRED`（多条读也是同一快照）。异常分支捕获 `BaseException` 并回滚，然后原样抛出，所以 D2 用 `BaseException` 模拟的 kill 也不会留下半截写入。
2. **持久性**：WAL + `synchronous=FULL`。D2 在调用处理器前先落 running，这一步如果在断电后丢失，重启会把已点过的指令当 queued 重做，所以没有用 NORMAL。实测单条 `put_command` 约 2400 次/秒（本机 SSD），远高于指令频率。
3. **整体存 JSON**：指令、结果、事件都按 `to_wire()` 存 JSON（`command_json` / `result_json` / `event_json`），读出时用契约模型重新校验，没有为结果字段建列；契约 0.2.0 拆分 `gui_write_performed` 不需要改表（但旧数据需要转换，见第七节第 1 条）。
4. **规则只用契约**：迁移调用 `require_transition("command" / "delivery", ...)`；"终态必须有 result、status 与 state 一致"由契约的 `LedgerCommand` 模型校验，账本不另写一份。
5. **排序**：`list_commands` 按接收时刻（整数微秒列 `received_at_us`，不同时区也正确）再按插入顺序；`pending_results` 按完成顺序（`finished_seq`，迁移到终态时分配）；`event_outbox.seq` 用 `AUTOINCREMENT`，删除或回滚都不会复用。
6. **CHECK 约束**：表上只约束稳定的部分（queued/running 时不得有 result/delivery、paused 时必须有 pause_reason、delivery 取值），终态枚举不写进 CHECK，契约新增终态时不需要重建表。
7. **迁移**：每一步一个事务，在同一事务里更新 `schema_version`，任何一步失败库都停在上一个完整版本；库版本比程序新时拒绝打开（不降级）。已发布的迁移不得修改，只能追加。

## 六、与内存替身的差异（SQLite 版更严）

共用契约测试覆盖的行为两者一致。以下只在 SQLite 版检查，已在 `test_ledger_sqlite.py` 单独测试（不带时区的时间两者都拒绝：内存版由契约模型的 `AwareDatetime` 拒绝，SQLite 版在写库前显式检查）：

- `limit` 必须是正整数（SQLite 的 `LIMIT -1` 表示不限，必须拦住）；
- 迁移到终态时 `result.command_id` / `action` 必须与账本中的指令一致。

## 七、接口请求

1. **契约 0.2.0 的旧数据兼容（给 A / 监督者）**：`CommandResult` 是 `extra="forbid"`，0.2.0 去掉 `gui_write_performed` 后，账本里 0.1.x 写入的 `result_json` 会读不出来。两种做法二选一：(a) 契约在 0.2.0 提供旧形状到新形状的转换函数（推荐，F2 服务端也会遇到同一问题）；(b) D1 跟进时追加迁移 v3，用 SQL 的 `json_set / json_remove` 改写 `result_json`。无论哪种都不需要改表结构，但需要监督者告诉我新字段在旧数据上的取值规则（例如 `gui_write_performed=true` 映射为 `outbound_action_performed=true` 还是三者都 true）。类别：契约缺口。
2. **InMemoryLedger 对齐（给 D2，可选）**：建议 `core/testing.py` 的内存版也加上第六节的两条检查，这样 core 的测试里如果出现错配的结果能早一点暴露。不影响当前测试。

## 八、未覆盖项与已知限制

- **不清理已回传的数据**：`delivered` 的指令与事件一直保留，库会持续增长。保留期限方案与契约都没有规定（产品取舍）；建议后续加 `prune(before=...)`，只删除终态且已 delivered、且早于 outbox 游标的行。
- **单进程使用**：内部用锁串行化，`check_same_thread=False` 允许 J/K 从其他线程调用；多个 Monitor 进程同时打开同一文件时 SQLite 本身不会损坏，但 `BEGIN IMMEDIATE` 会在 5 秒忙等后抛 `sqlite3.OperationalError`，没有做进程级互斥（应由 J 的 launchd 保证单实例）。
- **WAL 需要本地文件系统**：数据库放在网络盘上时 WAL 不可靠；`open_ledger` 在无法启用 WAL 时直接报错，而不是悄悄退回 rollback journal。
- **"kill -9" 的覆盖范围**：子进程测试验证了"提交前进程退出"；"提交过程中断电"依赖 SQLite 自身的 WAL 保证，没有也无法在单元测试里模拟。
- 老库识别：只认 `schema_version` 表；如果某个文件里有同名业务表却没有 `schema_version`（非本程序创建），迁移会因 `CREATE TABLE` 冲突报 `LedgerSchemaError`，不会尝试接管。
