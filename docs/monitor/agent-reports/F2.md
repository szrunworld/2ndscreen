## 实现概要

**存储**：`db.MIGRATIONS` 追加 v2，新增 5 张表：`recruitment_cases`（唯一键：账户 + 规范化姓名 + 规范化岗位）、`case_timeline`、`case_commands`（记录指令来源 auto / manual / recheck）、`case_resume_links`（简历关联与解析时间，供总览计数）、`policies`。F2 的存储类（`CaseStore`、`PolicyStore`、总览查询）与 F1 共用同一个 `SqliteStore` 连接和锁，用了它的 `_tx/_one/_all`。这样写 case 和写时间线在同一个事务里，换 PostgreSQL 时要另写这几个类。

**装配**（`main.py` 只做了追加）：`AppContext` 增加 `policies / cases / orchestrator / manual / overview` 五个字段；`create_app` 构造这些服务并注册 4 个 router。没有注入 `policy_version` 时，心跳的策略版本改由 `PolicyService.version` 提供。`app.router.lifespan_context` 包了一层：uvicorn 启动时开启编排的后台定时推进（60 秒一次），TestClient 不进入 lifespan，测试里直接调 `tick()`。

**流程（cases.py）**：阶段迁移只调用 `monitor_contracts.require_transition("case", …)`，没有另写迁移表。每次迁移用"当前阶段 = 预期阶段"做比较交换，并在同一事务里写一条 `stage_change` 时间线。`needs_human_reason` 在离开 needs_human 时清空。所有改 case 的操作（事件、结果、人工处理、定时推进）共用 `CaseService.lock` 串行执行。

**编排（orchestrator.py）**：订阅 F1 的 EventBus。
- `application_observed`：按（账户, 姓名, 岗位）建立 case；已存在就合并，事件关联到已有 case，不重复下发。岗位不在 `job_scope` 内的 case 不自动处理。
- 下一步挂在 `case.next_action` 上（问候开启时是 `send_greeting`，否则在 `auto_request_resume` 开启时是 `request_resume`），生成前先过 `PolicyService.gate`：白名单、策略暂停、账户下设备全部暂停、工作时段、每日上限。不满足时保留这一步并记录 `blocked_reason` 和一条时间线；事件到达、结果回报、保存策略、定时推进都会调用 `tick()`，条件满足后补发。
- 问候 succeeded：进入 greeted，生成 `request_resume`，`depends_on` = 问候指令。问候 skipped_precondition（界面显示已问候）：同样进入 greeted，但求简历不设依赖，因为领取要求依赖指令是 succeeded，设了会永远领不到。
- 问候或求简历结果为 unknown、failed、expired：转 needs_human（reason 分别为 `unknown_result` / `command_failed` / `command_expired`），不推进也不重发。cancelled 不改变阶段。服务端判定过期（从未被领取）时没有总线消息，由 `tick()` 发现后转人工。
- 求简历成功：进入 resume_requested，记录 `resume_requested_at`（取结果的 `executed_at`）。超过 `resume_mail_timeout_days` 仍没有关联简历时，`tick()` 把 case 转 needs_human（`resume_mail_timeout`）。
- `Orchestrator.issue(origin="auto")` 遇到 `request_contact_exchange` 直接抛 ValueError；自动流程只会生成问候和求简历两种指令。
- `contact_exchange_updated` 只更新 `contact_status`；状态为 available 且 case 处于 contact_requested 或 needs_human 时，进入 contact_available。`attachment_available` 让 case 从 new_application / greeted / resume_requested 进入 resume_received。`conversation_ambiguous` 建立（或合并到）case 后转 needs_human。

**人工处理（manual.py）**：四个接口都写 `manual_actions` 并记一条时间线，原始结果不改。
- `confirm-sent` 只接受 server_status=unknown 的指令（否则 409 `not_unknown`；同一条确认两次 409 `already_confirmed`）。确认后按"已发生"推进：问候 → greeted 并按策略挂求简历（不设依赖）；求简历 → resume_requested；换微信 → `contact_status=request_sent`，并从 needs_human 回到 contact_requested。
- `recheck` 复制原指令，改为新的 command_id、`execution_mode=verify_only`、`depends_on=null`，不过策略判定。对 search_candidates / provide_input 返回 409 `recheck_not_supported`。verify_only 的结果只写时间线，不推进阶段；之后是否确认已发送由人工 confirm-sent 决定。
- `stop` 把未领取的指令置为 cancelled；已领取的登记取消，由设备回报为准。随后 case 进入 closed。已经是 closed 时只补一条记录，返回 200。
- `request-wechat`：closed 返回 409 `stage_not_allowed`；已有未完成的换微信指令返回 409 `already_requested`（`existing` 中附上该指令）；策略判定不通过返回 409 `policy_blocked`（`errors[0].code` 是具体原因，工作时段外也算）。通过后生成 `request_contact_exchange(exchange_type=wechat)`，阶段进入 contact_requested；已在 contact_requested / contact_available 时阶段不变。

**策略（policy.py）**：账户已知（已有策略、设备绑定或 case）时，GET 会写入默认策略（版本 1，白名单为空，工作时段为周一至周五 09:00–18:00（上海），daily_limits 等于硬上限，min_interval 等于本地下限），返回时带 `ETag`。设备令牌只能读自己绑定账户的策略，读其他账户返回 404。PUT 规则：
- `If-Match` 不等于当前版本返回 412 `policy_version_mismatch`；写库用"版本相等才更新"做比较交换。
- `policy_version`、`updated_at`、`updated_by`、`company_mailbox` 由服务端覆盖，`company_mailbox` 固定为 `zhaopin@remotedesk.io`。
- 在契约校验之外另加四条：daily_limits 高于 40 返回 `exceeds_hard_limit`；min_interval 低于本地下限返回 `below_floor`；时区无法识别返回 `invalid_timezone`；时段窗口 start ≥ end 返回 `invalid_window`。
- 硬上限在服务端另写了一份常量。`test_hard_limits_match_monitor_client` 会与 `client/monitor/core/limits.py` 核对。

**总览（overview.py）**：统计日按账户策略时区。new_applications、resume_requested、resume_received、resume_parsed、unknown_results 统计当天的数量；needs_human 是当前积压，不按天计。各项分开计数，不合成一个"成功数"。devices 只列该账户绑定的设备，不指定账户时列全部设备。

### 1. 原子性（必须修）

**存储层**（`db.py`）：
- `SqliteStore._tx()` 改为可嵌套：最外层仍是 `BEGIN IMMEDIATE … COMMIT`，内层用 `SAVEPOINT` 嵌套。内层失败只回滚内层，外层失败整体回滚。
- 新增公开的 `Store.transaction()`，这就是"在调用方事务内插入指令"的接口：块内调用的 `insert_command`、`insert_manual_action`、`request_cancel` 等写方法，以及 F2 的流程表写入，都加入同一个事务。
- F1 已有的方法签名和行为都没变，F1 测试全部原样通过。`commands.py` 只在 `create_command` 的文档字符串里补了两行说明。

**F2**：
- `CaseService.atomic()` 先进入存储事务，再拿进程内锁。锁保留作额外保护；加锁顺序固定为"先存储、后流程"，F3 在自己的事务里调用 F2 时不会死锁。
- 以下操作现在各自在一个事务里提交，抛异常时整体回滚：
  - 总线消息的处理：建 case、生成指令、清 `next_action`、改阶段、写时间线；
  - `advance` 的每一步；
  - 人工的 confirm-sent、recheck、stop、request-wechat；
  - `link_resume`；
  - 转人工。
- **崩溃恢复**：F1 先提交事件或结果、再发总线消息，进程在两者之间崩溃（或 F2 处理抛异常回滚）时，记录会停在"已落库、未处理"。`Orchestrator.recover()` 由每次 `tick()` 调用，后台定时器启动时也会先跑一次，负责把这些记录重做一遍。判定依据与处理写在同一个事务里，所以不会重复处理：
  - 新投递 / 会话歧义事件：处理后 `events.case_id` 一定非空；
  - 指令结果：处理后一定有一条该指令的 `command_result` 时间线。
- 总线消息和恢复步骤都会先检查这两个标记，所以重复投递、或恢复与正常投递撞在一起时都只处理一次。`tick()` 的每一项各自一个事务，单项失败只记日志、不影响其他项。

**测试**（`tests/test_atomicity.py`）：
- 存储层：同一事务内一起提交或一起回滚；嵌套时内层失败只回滚内层。
- 在"指令已插入、登记或时间线还没写"时注入异常，覆盖五条路径：自动问候、问候成功后的求简历、人工换微信、recheck / stop、confirm-sent。断言：
  - 指令、人工记录、阶段全部回滚；
  - 重做或重试（同一个 Idempotency-Key）后恰好一条指令，case 状态与指令一致。
- 用文件数据库模拟两种崩溃："事件已提交、F2 未处理"和"结果已提交、F2 未处理"。在同一个库上重建应用、执行 tick 后，恰好一条问候、一条求简历，流程能继续推进。
- 重复投递已处理的消息不会重做；`recover()` 没有待处理记录时返回 0。

### 2. 产品取舍裁决的落实

### 已知限制

- 恢复步骤每次最多扫 200 条事件和 200 条结果，积压更多时分几次 tick 处理完。
- 进入工作时段后，顺延的换微信指令由 Monitor 正常领取。如果之后策略把工作时段改了，这条指令仍按原来算出的 `issued_at` 下发，或到期后过期。
