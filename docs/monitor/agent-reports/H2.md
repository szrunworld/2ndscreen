## 三、实现概要（`search.py`）

不是会话类动作，没有用 `ConversationSession`。复用 H1 的 `read_view`、`detect_blockers`、`Waiter`、`Evidence`、`Stop`、`norm` / `squash`、`not_allowed`，另写了一个小的 `SearchSession` 记录标志、facts、evidence。

**流程**：白名单 → 读界面（有弹窗就 unknown_dialog）→ 点左侧『搜索』（导航；0 个或多个都不点）→ 等唯一的关键词输入框出现（≤10 秒）→ 确认搜索按钮唯一 → **进入 `ctx.outbound()`**：有旧关键词就点输入框、cmd+a、delete 并核对已清空（≤2 秒）；输入关键词；核对 value 等于关键词（≤2 秒）；提交前再复核一次；记下结果区签名；点搜索按钮 → **退出 outbound**，等待结果（≤10 秒）→ 组装快照。

**元素规则**（窗口相对坐标，search_page#0）：

- 入口：AXLink，label 恰为『搜索』，x < 120。
- 关键词输入框：AXTextField，y < 80，宽 ≥ 300（城市输入框宽 66，不会混进来）。
- 搜索按钮：输入框右侧 40pt 内、中心在输入框纵向范围内、宽 40–160、无 label 的 AXGroup。
- 结果卡：宽 ≥ 500 的 AXLink。它的子元素取紧跟在它后面、中心落在卡片框内的连续元素（深度优先展开时后代紧跟在祖先之后）。
- 视口：窗口的纵向范围。高度 ≤ 1 的元素视为滚出视口。卡片边缘贴着视口边缘 1pt 内，视为被裁切。

**等待可识别状态**：每轮重新读取，按下面的规则判断：

- 有弹窗 → 立即停，unknown_dialog。
- 视口内有卡片 → results；有无结果文案 → empty；两者都有 → conflict（按 unreadable 处理）；都没有 → 继续等。
- 结果区签名（全部卡片 AXLink 的 label 加无结果文案）必须和提交前不同，并且连续两次读取一致，才认为结果已经稳定。前一条防止把热门词旧结果当成新结果，后一条防止读到刷新中的半截列表。

**卡片内容**：

- fields：卡片内视口可见的 AXStaticText，按树中顺序（左栏在前、右栏在后）。label 一律为 null：『期望城市』『职位』『院校』在界面上本来就是独立的静态文本，按顺序原样放进 fields，不配对，也不命名。
- 文本处理：去掉 Unicode 私用区的图标字符，用 `redact_text` 删除手机号、微信号、邮箱（兜底），截到 500 字，每张卡最多 60 条。
- masked_name：恰好一条文本匹配 `^[^\s*]{1,12}\*{1,4}$` 时取它，否则为 null。
- prop_card_texts：匹配 `道具|畅聊|直聊|聊卡|卡券|使用\S{0,4}卡` 的文本。

**选卡**：只取完整可见的卡片，按 y 排序，截到 max_results 张。一张完整可见的都没有时，退而取被裁切但有可见文字的卡片。只要有一张入选卡片读不出任何文字，整次就按 unreadable 处理，不回报部分结果。

**结局**：

| 情况 | status / reason | coverage |
| --- | --- | --- |
| 有结果 | succeeded | `partial`（不翻页、不滚动，无法确认已看到全部，一律 partial；从不报 complete） |
| 明确无结果 | succeeded | `empty_confirmed` |
| 超时 / 读不到 / 卡片无文字 / 卡片与无结果文案矛盾 | failed / `unreadable` | `unreadable`，items 为空，填 `unreadable_reason` |
| 入口或按钮找不到 / 歧义、搜索页不出现、核对失败、弹窗 | failed / 对应 reason | 不带 output |

超时也用 `reason=unreadable`，没有用 `timeout`：brief 要求"状态未知 → unreadable"，契约第五节规定 coverage=unreadable 时指令是 failed + `reason=unreadable`。`unreadable_reason` 与 `observed.after` 的 `search_result_timeout` 会注明是超时。只有"点『搜索』后搜索页一直不出现"用 `timeout`，因为那时还没有提交。

**执行标志**：用户 2026-10-04 决定"搜索算对外动作"，协调者已转达。点入口是导航；清空、输入、核对、提交都在 `ctx.outbound()` 里。所以只要进入过输入阶段，`outbound_action_performed` 和 `externally_visible_side_effect` 都是 true。输入核对失败时虽然已经进过 outbound，状态仍是 failed，不改判 unknown：搜索没有需要防重复的对方可见效果，重试最多多算一次搜索次数。这一点与 H1 不同。

**verify_only**：契约规定 search 只能 execute。崩溃恢复也会调用到这里。搜索没有可以复核的界面状态，所以不调用 driver，直接回报 failed / unsupported，管线会把它改判为 unknown / crash_recovery。

**Fact.code**：`search_page_opened`、`search_page_not_ready`、`search_keyword_present / cleared / not_cleared / entered / mismatch`、`search_submitted`、`search_results_visible`、`search_empty_confirmed`、`search_unreadable`、`search_result_timeout`、`target_not_found`、`target_ambiguous`、`unknown_dialog`。

## 四、未覆盖项

- 没有在真机运行。输入、提交以及提交后的全部界面都来自派生步骤。
- 不翻页、不滚动加载更多，所以 coverage 永远不会是 `complete`。

- 登录失效、验证码、风控页：以普通 AXButton 或 Sheet 形式出现时按 unknown_dialog 处理，其他形态最终落到 unreadable 或 timeout。`login_required` 和 `captcha` 这两个 reason 本任务不产出。
- `account_mismatch` 没有使用：契约 v1 没有检测手段。

## 六、需要协调者知悉

1. **执行标志前后改过一次，最终以用户决定为准**：搜索算对外动作，输入和提交包在 `ctx.outbound()` 里，三个标志都是 true。我中途问过一次，协调者先回复"按契约 / D2b 算导航"，随后转达用户的决定改了回来。现在的实现以后者为准。契约第四节的释义（"在搜索框输入关键词"属于 navigation）和 core 里 search 的特例由协调者另派任务修改，本任务没有改。
2. **与 core 的冲突，已用 strict xfail 标出**：`test_core_treats_search_success_as_outbound` 断言 `write_flags.success_is_outbound("search_candidates")` 为 True。现在 core 返回 False：崩溃恢复复核成功时，search 的 outbound 会被设为 false。H2 的 verify_only 永远不会回报 succeeded，所以这条路径实际走不到，但常量本身与新决定冲突。core 改完后这个用例会变成 XPASS 并让测试失败，到时删掉 xfail 标记即可。`counts_toward_limit` 对 search 的处理是"导航或对外动作"，与新决定兼容，不需要改。其他 core 行为（守卫计数、outbound ⇒ visible、管线合并标志）在端到端测试里与期望一致，没有冲突。
3. **超时的 reason 用 `unreadable` 而不是 `timeout`**，理由见第三节。如果服务端想区分，可以看 `unreadable_reason` 或 `observed.after` 里的 `search_result_timeout`。
4. **输入核对失败时 status 用 failed**，没有像 H1 那样在对外动作之后改判 unknown，理由见第三节"执行标志"。
5. 契约没有缺口需要修改。
