## 五、设计要点（给审查与后续任务）

1. **单线程 tick 模型**：`MonitorRuntime.run_once()` 每轮依次做 服务端往来 → 崩溃恢复 / 执行 → 观察 → 领取。长轮询的等待时间截到下一次心跳或观察到期为止，所以心跳不会被长轮询拖过 30 秒；但一个动作执行期间不发心跳（动作本身有 10 秒级上限，见 H1）。测试全部用 `run_once()` + ManualClock 驱动，没有真实 sleep。
2. **先落 running 再调处理器**：恢复时只调 `verify_only`，并且 Driver 外包只读守卫。复核结果映射：succeeded → succeeded（`gui_write_performed=true`，observed.after 加 `crash_recovery` 事实）；failed/verification_failed → failed/verification_failed（不重做）；其他或异常 → unknown/crash_recovery。
3. **白名单与限额 core 也查一遍**：除了处理器按协议自查，core 在 queued 阶段就按"策略白名单 ∩ 本地白名单"和限额拒绝，处理器根本不会被调用。
4. **最小间隔不直接判失败**：间隔未到时指令留在队列等待；等到会超过有效期才 failed(rate_limited)。每日上限到了直接 failed(rate_limited)。"每日"按策略 `work_hours.timezone` 划分，没有策略时按 UTC。计数只算 execute 模式下真正动过界面的执行（running 或结果标记为动过界面）。
5. **处理器异常与不合契约的结果**：DriverError 或其他异常时，若守卫计到写调用 → unknown/driver_error，否则 failed/driver_error；处理器返回不合契约的结果时同样按这个规则保守兜底，并记 `last_error`。
6. **暂停**：停止领取、启动新指令；心跳、ack 补发、结果回传、事件补传照常。暂停原因为 user_request / account_switched 时连观察也停（窗口不归 Monitor）；login_required / anomaly / server_request 时继续只读观察，观察到 `login_ok` 自动解除 login_required 暂停。服务端心跳 `paused=false` 只解除 server_request 类暂停。
7. **离线检测**：每次收到服务端响应（任何状态码）记 `last_online_at`（落盘节流 60 秒）。再次连上或进程启动时发现距上次在线超过 24 小时 → `needs_baseline=true`、基线重置为未建立（generation+1）。needs_baseline 期间不领取；观察器把 `baseline.established` 置 true 后才清除。
8. **4xx 不重试**：结果回报 4xx（非 409）、事件被 rejected 时，本进程内不再重发、留在账本并记 `last_error`（进程重启后会再试一次）。409 result_conflict 视为服务端已有结果，标 delivered 并记 `last_error`。401 → 停止全部服务端往来，`status()["revoked"]=true`。

## 八、未覆盖项与已知限制

- 未接真实 D1 SQLite 账本：所有测试用 `core/testing.py` 的 InMemoryLedger（按契约迁移表 + 深拷贝语义）。"kill -9"是进程内模拟（BaseException），不是真的杀子进程；真实账本的事务一致性由 D1 负责，端到端崩溃测试留给 M。
- 未接真实服务端（F1）：FakeServer 按 openapi.yaml 实现了 Monitor 用到的 6 个接口并用 `monitor_contracts.check` 校验请求体；F1 合并后应在 M 里跑一遍真服务。
- 工作时段（`work_hours`）不在本地强制：方案里由服务端在时段外不生成对外指令；本地只用它的时区划分"每日"。
- `policy.paused` 字段本地不单独处理，以心跳响应的 `paused` 为准。
- 动作执行期间不发心跳（单线程）；若 H 的某个动作可能超过 60 秒，需要另开心跳线程。
- `client_state` 是根据执行与观察结果推断的（running / login_required / blocked_by_dialog / not_running / unknown），不主动探测客户端进程，J/K 可以按需补充。
- 观察器读不出界面时如果不把 `baseline.established` 置 true，needs_baseline 会一直保持、不领取指令——这是有意的（"不猜"），E 需要知道。
- 观察与 verify_only 时 scroll 也被只读守卫拒绝；如果 E 需要滚动读取列表，需要改守卫规则（B 已发现会话列表后台滚动无效，所以暂未放开）。
- 硬上限数值未经用户确认（第六节）。

## 九、对后续任务的接入说明

- **H1–H3（动作）**：实现 `ActionHandler`；拿到的 `driver` 是 `GuardedDriver`，写调用会被计数，verify_only 时任何写调用抛 `ReadOnlyViolation`。`ctx.allowed_actions` 已是策略 ∩ 本地白名单；core 已在前置检查拦掉白名单与限额，处理器仍须按协议自查。返回 `login_required / captcha / unknown_dialog / account_mismatch` 会让设备暂停并上报，`target_ambiguous` 只让本条失败。
- **E（观察）**：`observe(driver, baseline)` 拿到的是只读守卫；就地修改 `baseline`，确认读到界面后把 `established` 置 true；返回的 `login_required / blocked_by_dialog / login_ok` 事件会驱动暂停与恢复。core 负责落 outbox 与补传。
- **J（状态窗口 / 安装）**：`runtime.status()` 给出窗口所需字段；"暂停并归还窗口"调 `runtime.pause("user_request", by="user")`，恢复调 `runtime.resume()`；换账户确认后调 `runtime.bind_account(account_id, confirmed_by=...)`。GUI 执行权用 `runtime.gui_lock`。
- **K（登录接力）**：需要操作界面时用 `with runtime.gui_lock.hold(ACTION):`，截图直接用原始 Driver（守卫不允许截图）；登录完成可直接发 `login_ok` 事件或调 `runtime.resume(by="monitor")`。
- **M（集成）**：`monitor.core.testing` 的 `FakeServer`、`InMemoryLedger`、`make_env` 可直接复用；`Env.new_runtime()` 用同一账本模拟重启。
