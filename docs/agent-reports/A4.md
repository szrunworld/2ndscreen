## 实现要点

### 页面与安全（pages.ts）

- 分类顺序：captcha → request_resume_dialog → loading → online_resume → attachment_preview → login → popup → conversation_detail → conversation_list → unknown。会话与列表直接复用旧 `chat()`、`conversations()` 解析器。
- 在线简历按 P0 的元素结构识别：小于窗口的 AXWebArea 内有一张占满它的 AXImage，旁边有 举报/转发 操作列。出现“正在加载简历”时判为 loading，不当作已打开。关闭控件是覆盖层右上角无文字的约 30×30 元素（P0 正是点击该位置关闭），找不到时才用 Escape。
- 索取确认框按 P0 文案“确定向牛人请求简历…”识别，同时定位 取消 和 确认 两个按钮。确认按钮只做定位，从不点击。
- 所有非候选人行的点击都先经过 `assertSafeLabel`。凡标签涉及发送、求简历、请求/索取、换电话/微信、约面试、不合适、继续沟通、打招呼、确认/确定、举报、转发、收藏等，一律以 `forbidden_effect` 拒绝。动作效果只有 read/navigation（采集单元另有 artifact），不使用 external-submit。

### 候选人与身份（candidates.ts）

- 列表引用 `sourceRef` 由姓名、职位、时间和预览哈希组成，只在当前快照内有效。职位筛选设为某职位时，排除其他职位的行。
- 完全相同的两行标为 `duplicate_row`，拒绝打开。同一列表中同名同岗的两行标为 `name_job_collision`；工作流按账号记住这一对，之后行重排、其中一行滚出视野，后续引用仍带此提示，`identify` 返回 ambiguous。
- `identify` 的判定规则：
  - 姓名与职位必须一致，任一侧没有职位即为 ambiguous。
  - 只有姓名、没有摘要和经历时为 ambiguous。
  - 指纹 = 账号 + 姓名 + 摘要 + 经历行的哈希，`candidateId = c-<24位hex>`，可通过 `safePathSegment`。
  - 摘要和经历都有时为 strong，只有其一时为 weak，并在证据中写明 `confidence weak`，由 runner 显式处理。
  - 证据和不一致信息只写哈希标签，不含姓名。
- `open_candidate` 每次都重新读取并重新定位行。行已移动（新消息改变时间和预览）时，按姓名+职位唯一匹配找到它。点击后轮询，直到会话头部是同一人；打开错人不会成功。verifyUnit 还会核对 work item 已绑定的指纹。
- 职位选择：标题完全相同则直接采用，否则要求只有一个包含该文本的选项。多个匹配返回 `job_ambiguous` 且不选择任何项；无匹配返回 `job_not_found`。

### 列表进度（按早期审查修订）

- `listEnded` 只认列表栏内、且不在任何行范围内的“暂无牛人/没有更多”提示。预览或聊天中的相同文字不会结束列表；最后一行下面有空白也不算结束。
- `advance_list` 依次判断：
  1. 向下滚动后出现新行，即成功。
  2. 最后一行被截断说明后面还有内容，此时列表不动判为 `scroll_ineffective`。
  3. 列表中有“加载中”字样时返回 `list_still_loading`。
  4. 探测：向上滚动列表会变，再向下滚动回到完全相同的行，才确认到底。
  5. 两个方向都滚不动时，只有短列表才可能到底（最后一行完整、下方留空），且须在设定的等待时间内保持不变、没有加载提示。
- 由探测确认的结束会记录对应 snapshotId，`verifyUnit('advance_list')` 据此判定成功。其他情况比较 `bindings['list.fingerprint']`。

### 在线简历采集（capture.ts）

- 没有注入 vision 时返回 `failed / local_vision_missing`，不做任何推测。
- 每屏都重新读取覆盖层并截取同一区域；覆盖层消失或面板移动时停止。
- 回顶：向上滚动直到画面不再变化，并且首屏顶部 OCR 出现 BOSS直聘 标志，才算 `topConfirmed`。
- 展开折叠：只点击 OCR 文字恰为“查看全部”且位于面板内的位置。点击后必须看到“查看全部”减少或“收起”增加；否则记为未展开，结束原因按 `stitch_gap` 处理（内容有缺口）。
- 向下滚动：每屏与上一张保留的截图比较，记录位移。重叠少于 `minOverlapPx` 时退回并把步长减半重试一次，仍不够则停为 `stitch_gap`。
- 到底判定（与协调者确认）：
  - 连续两次向下滚动画面不变，只触发检查。
  - `end_marker`：页脚说明（“为妥善保护牛人在BOSS直聘平台提交…”“在线浏览牛人简历”）出现在屏幕最后几行，下面没有内容。
  - `scroll_position_end`：之前确有向下进展，从末屏向上滚动画面变化，向下滚回同一画面，再向下仍不变。探测用的截图不保留。
  - 两个信号都具备才是 `bottom_confirmed`。只有一个信号或不满足条件时为 `scroll_ineffective`。空白边距不算信号。首屏永远不会判为完整。
- 页数上限 → `page_limit`；滚动失败 → `scroll_ineffective`；`compose` 的 hasGap 或 gap 帧 → `stitch_gap`。完整性由 `captureCompleteness` 判定。
- 身份关联：覆盖层旁的姓名，或首屏 OCR 中的姓名，至少一个与列表姓名一致，否则返回 `failed / resume_identity_unconfirmed`。
- 产出（全部写在 `context.staging` 内）：
  - `pages/page-NNN.png`（captured_page）。
  - 有 `compose` 时生成拼接图（captured_image，带采集证据）；没有时不生成，metadata 记 `compose_unavailable`，因此不计数。
  - `resume.txt`：后一屏只取上一屏已识别内容以下的行，跨屏被截断的行由下一屏补上。
  - `metadata.json`：只有哈希、尺寸、位移、证据和问题项，不含姓名和正文。

### 附件分支

- P0 未验证下载路线，默认关闭（`ATTACHMENT_ROUTE_OFF`）。
  - `captureMode = original-only` 时，`select_source` 和 `acquireResume` 都抛 `capability_missing`，不点击附件简历，也不打开任何候选人。
  - `available` 模式不探测附件，直接走在线简历。
- 通过 `createBossResumesWorkflowWith({ attachment })` 显式开启后的流程：
  1. 点击“附件简历”。
  2. 出现索取确认框时只点 取消，并确认它已消失，返回 `unavailable / request_dialog`。取消失败返回 `failed / request_dialog_not_dismissed`。
  3. 打开预览后，在下载目录中等待恰好一个新的、已完成、大小稳定的文件。
     - 出现多个新文件：`download_ambiguous`。
     - 一直是 .crdownload 等临时文件：`download_timeout`。
     - 文件名不含候选人姓名：`download_identity_unconfirmed`。
     - 文件头不是 PDF/DOCX/DOC：`download_unrecognized`。
  4. 校验通过后复制到 `staging/original/`。
- `available` 模式下附件不可用时，回退到在线简历采集。

### 单元与验证

- `units` 覆盖 `BOSS_UNITS` 的八个单元，`persist_candidate.allowedEffects = ['artifact']`，任何单元都不含 external-submit。select_source、enumerate、acquire、persist、advance 不可学习；open_candidate、open_resume、return_to_list 可学习。前后条件都通过 `validateCondition`。
- `runScripted`：acquire_resume 和 persist_candidate 返回 undefined，由 `acquireResume` 和 ArtifactStore 负责。其余单元有确定的脚本路径。
- `verifyUnit` 是唯一的成功依据：
  - acquire_resume 检查暂存目录：有已完成的非空文件，且没有半成品。
  - persist_candidate 要求 item 已是 committed。
  - 其余单元按新的观察结果判断。

## 接入说明（给 A6/A7）

- 使用的 bindings 键：`job`、`candidate.name`、`list.fingerprint`（advance_list 之前那次列表的指纹）。
- 失败原因字符串：`job_ambiguous`、`job_not_found`、`login_required`、`captcha`、`candidate_row_ambiguous`、`candidate_not_in_list`、`conversation_not_opened`、`identity_ambiguous`、`identity_mismatch`、`request_dialog`、`resume_load_timeout`、`resume_identity_unconfirmed`、`scroll_ineffective`、`list_still_loading`、`list_end_unconfirmed`、`end_reached`（advance_list 成功并到底）等。前四个可直接映射到 WaitReason。
- 不支持的路线（recommend 来源、未开启附件路线时的 original-only）抛 `RuntimeError('capability_missing')`，建议映射为 `waiting_user / capability_missing` 或直接失败，不要逐个候选人重试。
- `readAccount` 始终返回 undefined：P0 没有在窗口中找到可靠的账号标识。任务需要显式绑定账号（`binding: 'explicit'`）。`open_candidate` 和 `advance_list` 在任务没有账号时抛 `invalid_input`。
- `identity.confidence === 'weak'` 时应由 runner 显式决定，例如标为 ambiguous 或需要确认，不应默认当作强身份归档。

## 未验证项与限制

- **真实 BOSS 从未操作。** 所有测试都用合成夹具。页面结构参考 P0 的本地证据（只按角色和位置读取元素树，仓库中没有任何真实素材）。P0 没有覆盖、因而在真实应用上未验证的有：
  - 职位筛选下拉的选项结构（按“新出现在某位置的文字”识别）；
  - Escape 关闭弹层；
  - 列表滚动量与“没有更多”提示的真实文案；
  - 登录与验证码的文案；
  - 附件预览及其“下载”控件；
  - 覆盖层旁姓名所在位置（按 P0 结构推断）。
- 原始附件下载路线未验证，默认关闭；文件名须含候选人姓名这一关联规则同样是假设。开启前必须先由协调者实测。
- recommend 来源未实现，返回 `capability_missing`。
- 拼接依赖 A8 的 `compose`。本模块只用 fake 测试了 compose 结果的处理；没有用真实 helper 跑过合成截图，因为合成截图是很小的 PNG，没有可供比较的纹理。
- 在线简历底部的完整性只按上述两个信号判断。页脚文案来自 BOSS 1.7.4 的 P0 OCR，版本变化会导致只能得到部分采集，从而报告 partial，不会误报完整。
- 指纹包含摘要和经历，候选人更新经历后会成为新的 candidateId；同名同岗且历史相同的两个人无法区分（按同一人处理）。同名同岗一旦被记住，就一直是 ambiguous，宁可漏采也不错配。
- 短列表结束只依赖“滚不动 + 设定时间内不变 + 无加载提示”（默认 1.5 s）。如果真实列表在更长时间后才懒加载，会提前结束。真实验收时应确认实际加载延迟。
- 隐私：读取 P0 本地证据时，因过滤条件不够严，有少量会话预览文字输出到了本地终端。没有写入任何文件，也没有提交。
