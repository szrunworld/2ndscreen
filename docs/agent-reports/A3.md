## 行为要点

**ProcedureEngine**（依赖只有 repository、rule、telemetry、clock、newId，没有任何模型或探索器）

- `select`：按 stable > trial > seeded 选择，同一状态内取较新版本；跳过 degraded、retired、key 不一致的版本，以及不能通过 `validateProcedure({submitAllowed:false})` 的版本（例如含元素 index 或 external-submit）。
- `replay`：动作执行前先拒绝以下情况：不合法或越权的流程（`invalid_input`）、degraded/retired 版本（`conflict`）、参数没有绑定值（`invalid_input`）。槽位绑定会覆盖步骤和条件；写入 `labelPattern`、`pattern`、`titlePattern` 的值先做正则转义，所以 “李(前端)” 只匹配它本身。执行顺序：
  1. 检查前置条件，不通过返回 `precondition_failed`，不执行任何动作。前后条件中任一层出现 OCR 或模板定位器时，观察会请求截图（`needsScreenshot`）。
  2. 按步骤执行。主定位器失败时按顺序尝试 fallbacks，但只在动作未送达（`failed`/`stale_snapshot`）时才换定位器；`no_effect` 只有 read/navigation 允许换；结果为 `unknown` 的动作一律不重发。
  3. `expect` 通过 `session.waitFor` 做有界等待。
  4. 最后用新观察检查后置条件。
  
  取消返回 `cancelled`。每次回放记录一条 telemetry `unit/replay` 事件。
- `recordOutcome`：调用 `nextProcedureState`，只改 status、counters、updatedAt。
- `rollback`：做法是复制定义，插入为最新版本（`parentVersion` 为目标版本，连胜清零，保留累计 successes 供审计），旧版本不改动。仍为 stable 的目标恢复为 stable。degraded 的目标恢复为 **trial**：累计 successes 可能来自被失败打断的多段连胜，不能证明它曾经晋级过，所以要重新获得三次连续成功。seeded、trial、retired 和没有成功记录的版本一律拒绝（`conflict`）。
- `importV1Procedure`：只导入每一步（wait 除外）都是对有名称控件的 click、type 或 scroll 的 V1 流程。`⟦n⟧` 转为 `{{slotN}}`，`⟦n⟧…` 转为 `labelPattern: ^{{slotN}}`。以下情况一律返回 undefined：key 按键、没有目标控件的 type/scroll、未命名控件、按视觉偏移点击、`allowSubmit=true`。结果固定为 seeded、计数为 0、版本号为 1，不写回 `~/.config`。

**Learner**

- `propose`：
  - 拒绝以下轨迹：unit 与 key 不一致、不可学习的单元（`invalid_input`）；含单元不允许的效果或 external-submit（`forbidden_effect`）。
  - 只丢弃没有产生效果的步骤（failed/no_effect/stale）；结果为 unknown 的步骤保留。
  - 模型给出的坐标映射为解析到的语义控件（role+label），原坐标保留为 fallback；只有元素 index 而无法存储的步骤报 `invalid_input`。
  - 只在 label、text、value、各类 pattern 字段里把绑定值替换为 `{{slot}}`（长度 ≥2，最长的值优先）。
  - 页面类别发生变化的步骤加 `expect` 等待。
  - 输出前用 `validateProcedure` 自检。
- `accept`：证据必须同时满足 `ok=true` 且有非空字符串，否则 `invalid_input`，不写入任何东西。版本号取该 key 下最大版本 +1，指定的 `parentVersion` 必须存在。新版本状态为 trial，计数 `successes=1, successItemIds=[itemId]`，即本次验证成功算连胜的第一位。存入的是 proposal 的深拷贝。并发写入撞版本号（`conflict`）时最多重试 3 次。

**Recovery**

1. **本地恢复**：最多 `budget.localRecoveriesPerStep` 次，每次都记录 `local_recovery` 事件，依次尝试：
   - `wait`：有界等待单元后置条件，上限 min(unit.timeoutMs, 15 s)，再由 `context.verify` 复核。
   - `relocate`：仅用于 `step_failed`，且失败步骤上一次发送确定没有生效（failed/stale，或 read/navigation 的 no_effect；unknown 和 artifact 的 no_effect 不重发）。从失败步骤开始，用新解析的定位器继续回放；之前已执行的步骤不再发送。截出的这段流程必须先通过当前单元 allowedEffects 的检查。
   - `local_procedure`：改用另一个至少验证成功过一次、并且在单元允许范围内的版本。
   
   `no_procedure` 直接跳到第 3 步的探索。墙钟预算同样约束本地恢复：每条路线开始前和本地恢复结束后都会检查，已超时则返回 `exhausted: wall_clock`，连观察都不做；等待时长也会截到剩余时间以内。
2. **结果不明的步骤**：失败步骤结果为 unknown、且效果是 artifact 或 external-submit（或无法确定效果）时，返回 `exhausted: 'local'`，不交给模型重做。
3. **模型修复**：开始前依次检查本候选人的修复次数和 `checkBudget`，不满足就返回 exhausted，此时连 `explorer()` 都不调用。
   - `explorer()` 抛 `model_unavailable` 时返回 `{status:'model_unavailable'}`。
   - 请求经 `validateExplorationRequest` 校验：`submitAllowed:false`，allowedEffects 去掉 external-submit，后置条件已绑定参数。maxRounds、maxTokens、timeoutMs 取剩余预算与单元上限中的较小值。
   - 探索在 `withExclusiveActor('bridge')` 内运行。每个 `model_usage` 事件立即记为 telemetry `model_call`，带上 purpose、reason、token，未知 token 保持 `'unknown'`。
   - 出现以下情况就通过 AbortSignal 停止 Bridge：模型调用超过整任务次数上限；设置了 token 上限而 token 超限或未知；轮数超过本次上限；出现越权动作。
   - Bridge 实际调用次数多于上报事件的部分，按 unknown token 补记。
   - 越权动作在子进程退出后抛 `forbidden_effect`。
   - 超出整任务次数或 token 上限的 Bridge，即使已经 finished 且页面验证通过，也返回 exhausted，不算 repaired；超出本次轮数上限按失败尝试处理。
4. **验证与提案**：Bridge 返回 finished 后，recovery 重新观察，并独立调用 `context.verify` 复核。复核通过时用 `learner.propose` 从 `outcome.executed` 生成提案：修复场景的 source 为 `repair`，并在能确定失败版本时设置 `parentVersion`；首次探索的 source 为 `learned`。recovery 不重发 Bridge 已执行的任何动作。探索失败或复核不通过时，在本候选人的修复次数预算内重试，用完返回 `exhausted: 'item_repairs'`。
5. **入库由调用方完成**：recovery 不调用 `learner.accept`。按契约第 4 步，由 runner 调用 `learner.accept(proposal, verification, itemId)`，避免两边重复插入版本。

主要覆盖：

- **20 位稳定候选人**：engine 工厂没有模型依赖，`modelCalls=0`，`replayedUnits=20`，状态保持 stable。
- **完整学习闭环**：第 1 位探索，第 2 位立即复用 trial，第 3 位后晋级 stable，20 位总共 1 次模型调用；探索期间 `session.act` 为 0 次，即 Bridge 的动作没有被重发。
- **晋级与降级**：同一 item 重复成功不推进晋级；任何失败都清空连胜；降级阈值 1 和 2 都测了。
- **前后条件与回放**：前置条件挡住错误的候选人；fallback 定位器能确定性地恢复；unknown 结果不重发；有界等待能等到慢页面，也能在页面不出现时按时失败；取消有效；越权和不可运行的流程在执行前被拒绝。
- **回滚与版本**：回滚插入新版本，旧版本定义字节不变；成功与失败交替出现后降级的版本回滚为 trial，需要再连续成功三次才晋级；trial 版本和没有成功记录的版本不可回滚；proposal 版本按 key 递增；`parentVersion` 必须存在；并发冲突后取下一个版本号。
- **无效证据**：ok=false、证据为空、证据为空白字符串、缺少字段，都不写入。
- **预算**：本候选人修复次数、整任务调用数、上限下的未知 token、墙钟时间，都在调用 `explorer()` 之前就停止；Bridge 中途超出调用数会被中止，已发生的调用全部计量；token 上限下出现 unknown token 时停止。
- **模型不可用**：返回 `model_unavailable`，同时稳定流程照常回放。
- **协调者评审补充**：墙钟预算用完时本地恢复不做任何观察或动作，剩余 60 ms 时等待被截短；Bridge 超出整任务次数上限后即使页面到达也不算修复；超出轮数上限算失败尝试；relocate 不重发当前单元不允许的步骤，也不重发结果为 unknown 的导航步骤；任一层嵌套的 OCR/模板条件会请求截图；V1 的 key 按键和无目标的 type/scroll 被拒绝。
- **其他失败路径**：探索失败后在预算内重试；Bridge 声称完成但验证失败时不入库；越权动作抛 `forbidden_effect` 并归还动作权；取消发生在开始前时不创建模型客户端，发生在探索中时 Bridge 被中止，并在确认退出后返回；结果未知的 artifact 步骤不交给模型。

## 接入说明与限制

- **telemetry 记数**：engine 注入 telemetry 时，每次 `replay` 都记一条 `unit/replay`（ok 表示回放本身是否成功）。recovery 内部的 relocate 和 local_procedure 也会经过 engine 回放，所以同样会产生这类事件。如果 A6 自己也计 `replayedUnits`，要么不给 engine 注入 telemetry，要么不再重复记录，否则会重复计数。recovery 对每次探索记一条 `unit`（route 为 explore 或 repair）。
- **失败版本的查找**：契约中的 `ProcedureEngine` 没有按 id 读取版本的接口，recovery 的依赖里也没有 repository。所以 recovery 只能在 `engine.select(key)` 恰好返回失败版本时（即尚未降级）拿到它的定义。这决定了 relocate 和修复提案的 `parentVersion` 是否可用。如果 runner 在调用 recover 之前就记录了失败，导致版本已降级，relocate 会被跳过，提案也不带 `parentVersion`，但提案本身仍可用。如果需要稳定可靠的 parent，需要协调者在契约中补充按 id 读取版本的接口。
- **本地恢复次数**：`localRecoveriesPerStep` 是 wait、relocate、local_procedure 三条路线共用的总次数。默认值为 2 时，`step_failed` 只会走到 wait 和 relocate，不会走到 local_procedure。
- **结果未知且版本已降级**：如果失败版本已经降级、无法确定失败步骤的效果，unknown 步骤会被保守地当作 artifact 处理，返回 `exhausted: 'local'`。
- **V1 导入**：
  - 版本号固定为 1，插入已有版本的 key 时由调用方重新编号。
  - 效果按动作类型推断：click、type、key 视为 navigation，scroll 视为 read。V1 的 `allowSubmit=false` 保证这些步骤不是提交动作。
  - V1 的 `endControls` 不转换为后置条件，导入结果总是 seeded，需要在这里重新获得晋级证据。
- **promoteAfterSuccesses=1**：`accept` 保存的版本是 trial，要在下一次 `recordOutcome` 后才晋级。learner 的依赖里没有晋级规则，因此不在 accept 时直接晋级。
- **未验证项**：Session 和 Bridge 都是 fake，没有和 A1、A5 的真实实现联调，也没有在真实 BOSS 上验证。fake 只模拟“候选人详情 → 在线简历”两页。
