# 适配器窗口几何加固（绑定与截图）

## 范围

分支 `szrunworld/ss-a4-live`，基于 `6b1690d`。只改 `packages/task-runtime/src/adapters/second-screen.ts` 及其测试 `second-screen.test.ts`。没有改原生代码、BOSS 采集或其他模块；没有接触 GUI、私有文件或 `/tmp/2ndscreen-p0`。全部使用合成几何。

## 从代码确认的原因

1. `bindApp` 只在 `state` 失败（窗口中心不在目标屏上）时才 `window move --fill`。窗口中心在屏上但有一部分伸出屏外，或窗口比屏幕还大时，都不会移动它。
2. `mainWindow` 只检查最小宽度和连续两次读数稳定，不检查窗口是否完整位于屏内。屏幕 frame 也是在启动前读的，之后不会刷新。
3. 原生 `Images.crop` 用 `CGImage.cropping` 把屏幕截图裁成窗口区域，超出画布的部分会被**静默截掉**。而适配器把整张 PNG 标成 `covers = 窗口 frame`，再做区域裁剪；图像比 frame 小时，每个点的映射都会错。这与 P0 现象一致：窗格截图应为 1468×1750，实际是 913×1102。

## 修改

**绑定（`bindApp`）**
- 拿到稳定的主窗口后，**重新读取**目标屏的 frame（显示器可能已经移动），要求窗口完整位于屏内，允许 1 pt 的取整误差。位于菜单栏下方、比屏幕窄但够宽的窗口都算合法。
- 不在屏内时：
  - 既不是本运行时启动的，也没有 `takeOver`：抛 `conflict`，消息带窗口和屏幕的几何信息，**不做任何移动**。
  - 本运行时启动的，或有 `takeOver`：执行 `window move --screen … --pid … --window-id <id> --fill`，然后重新等待窗口稳定、重新读屏幕并检查。最多重试 2 次，仍不在屏内就抛 `conflict`。
- 返回的 `geometry` 使用刷新后的屏幕记录。

**截图（`observe`）**
- 带截图时，PNG 尺寸必须等于窗口 frame × 绑定的缩放比（`window.scale`），允许 1 像素误差（原生裁剪会向外取整）。
- 不符合时删除这张图，按需刷新屏幕列表，抛 `window_lost`，消息写明实际像素、窗口 frame，以及窗口是否伸出屏幕。绝不把被截掉的图当成整个窗口。
- 尺寸符合时行为不变，也不会多调一次 CLI。

进程身份核对、不抢前台、取消与超时、完整性判定、截图尺寸变化时的拒绝，都没有改动或放宽。

## 测试（合成）

`second-screen.test.ts` 新增 7 个，共 32 个，全部通过：
- 辅助函数：屏内、整个可见区域、半点取整误差算在屏内；伸出右边缘、超大居中算不在屏内。截图覆盖判断接受 2880×1750 对 1440×875 和多 1 像素的情况，拒绝被屏幕边缘截掉的图和 1x 图配 2x 窗口。
- 没有 `takeOver`：伸出右边缘和超大居中两种情况都抛 `conflict`，消息和 details 带几何信息，没有任何 `window move` 或 `app launch`。
- 有 `takeOver`：超大窗口按 window id 重新铺满一次，绑定到稳定后的 1440×875。
- 重新铺满后仍伸出：恰好 2 次后放弃，抛 `conflict`。
- 屏幕原点在绑定过程中移动：窗口按新位置判断在屏内，正常绑定，不移动。
- 本运行时启动的窗口伸出时：不需要 `takeOver` 也会重新铺满。
- 截图被屏幕边缘截掉（2480×1696 对 1360×848 的窗口）：抛 `window_lost`，消息说明伸出屏幕；不带截图的读取正常返回实际 frame。
- 原有的绑定、读取、区域裁剪测试全部通过。

结果：`packages/task-runtime` 类型检查通过；全部 379 个测试，368 通过、11 跳过（原有，在其他文件）、0 失败。

## 取舍

- 窗口超出屏幕时，截图读取直接失败（`window_lost`），不尝试只用可见部分。这样后续步骤和恢复逻辑不会拿到错误的坐标，代价是需要重新绑定或重新铺满。
- 截图覆盖判断依赖绑定时记录的缩放比。如果中途切换了 HiDPI，判断会失败，读取也会如实失败，而不是去猜缩放比。
- 绑定时多了一次屏幕列表读取；只有窗口伸出时才会有窗口移动和最多 2 次额外的稳定等待（每次至少约 1 秒）。
- 运行时自己启动的窗口不需要 `takeOver` 就会重新铺满：启动时本来就带了 `--fill`，这只是同一意图的重试。
- 原生裁剪本身没有改：截掉部分会在适配器这里被识别出来。原生侧是否改为直接报错，留给负责原生代码的人决定。
- 真实应用中的验证由主线负责。
