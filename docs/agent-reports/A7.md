## 设计

### 进程模型

- **CLI**（main.mjs）：每条命令打开账本，建一个 `claim:false` 的 daemon，只做一次控制调用，输出一行 JSON 后退出。`run` 和 `resume` 返回前调用 `ensureWorker`。如果 worker 起不来，会报错并在 details 中带上 taskId，说明任务已经记录。帮助信息和参数错误不会打开任何文件。
- **worker**（worker.mjs）：由 A6 的 `spawnDetachedWorker` 启动，是新进程组的组长，不继承 stdio，日志写入 `tasks/worker.log`。CLI 退出后它继续运行。以下情况会退出：
  - 收到 SIGTERM、SIGINT 或 SIGHUP，退出前由 daemon.shutdown 把运行中的任务转为 paused；
  - 空闲 10 分钟（`SECONDSCREEN_WORKER_IDLE_MS` 可调）；
  - 连续 35 秒拿不到 daemon 租约，说明它是重复实例，退出前不做任何动作。

  离开前它会关闭账本再重新检查一遍：如果有在它看完之后才排队的任务，就先拉起下一个 worker。
- **启动去重**：并发的 CLI 通过一个短租约 `2ndscreen.task-spawn:*` 轮流执行。轮到的 CLI 用 A6 的 `ensureDaemon` 等待 worker 真正持有 daemon 租约，后面的 CLI 再看时就会发现它。实测 6 个并发 CLI 只启动了 1 个 worker。
- **崩溃之后**：daemon 租约在到期前仍登记着已死的 worker。CLI 这时会启动一个候补 worker，并等它的进程记录出现后才放行下一个 CLI。候补在旧租约到期后接管任务，任务交给 A6 的孤儿处理流程。

- 适配器：`createSecondScreenAdapter`。其中 `run` 为 `registry.wrapRunner(createCommandRunner())`；`screenshotDir` 是每个 worker 自己的 `tasks/screenshots/<pid>`，权限 0700，在第一次 observe 之前创建，worker 退出时删除；启动时清理已经不存在的 worker 留下的截图目录。`app` 只在 Runtime 位于 .app 内时推导，也可由 `SECONDSCREEN_APP` 指定。
- 每个 Skill 各自创建：
  - `createSessionManager`，policy 取自 task.json；
  - `createProcedureEngine`，**不注入 telemetry**，`promoteAfterSuccesses` 取自 Skill；
  - `createLearner`；
  - `createRecovery({ telemetry: hub.shared })`；
  - `createBossResumesWorkflow({ vision, telemetry: hub.shared })`；
  - `createTaskRunner({ telemetry: hub.forTask })`。

  runner 按 `task.skillId` 分发。
- explorer 是惰性的：`async () => createAgentBridge({ cli, spawn })`，只在 recovery 确实需要探索时创建。稳定路径和脚本路径从不启动模型，没有模型配置时得到的是 A6 的 `waiting_user / model_unavailable`。

- 遥测：截图与 OCR 计数只来自 A4 workflow（`hub.shared`）。vision 和 session 不记录这两项，engine 不注入，所以没有重复计数。

### 账号（显式绑定，不猜测）

- `run … --account KEY`：调用 A6 的 `submit(skillId, input, { account: { platform:'boss', accountKey: KEY, binding:'explicit' } })`，在 `task_published` 之前写入账号。
- `bind-account TASK_ID KEY`：调用 A6 的 `bindAccount`，只用于 paused 或 waiting_user 且尚未绑定账号的任务，已绑定的 key 不会被改。
- KEY 必须匹配 `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`，不能含 `:` 或 `/`。如果 control 没有 `bindAccount` 方法，返回 `capability_missing`，不会悄悄丢掉用户给的账号。
- 没有 `--account` 时 CLI 不编造账号，任务进入 `waiting_user / account_changed`。没有提供全局账号配置：配置文件过期会在用户换号后把错误的账号静默标成 explicit。

### 进程记录与退出核验（actors.ts）

记录文件为 `tasks/actors/<pid>-<startMs>.json`，0600，原子写入并 fsync，内容如下：

- worker 的 pid、pgid，以及由 A6 的 `processStartTime` 读到的启动时间。启动时间与 A6 写进 `WorkerRecord.processStartedAt` 的值来源相同，按完全相等比较。
- `pendingSpawns`：spawn 之前先写 +1，spawn 返回后在同一次写入里减 1 并加入该组。
- `groups`：LineProcess 子进程组，含 `spawnedAfterMs`、`spawnedBeforeMs`（spawn 前后的两次时钟读数）。
- `commands`：A1 正在执行的命令（见下文“发现”）。
- 运行期间每 2 秒刷新一次 mtime，作为心跳。
- 只有在所有组和命令都已确认结束时，才在退出时写 `closedAt`。

`verifyWorkerStopped` 只在以下条件全部成立时返回 stopped:true：

1. 不是 legacy 记录，且有 `processStartedAt`；能找到与 pid 和启动时间完全匹配的记录，记录格式合法（pid、pgid 大于 1，pending ≥ 0）。
2. worker 已不在运行：pid 不存在，或已被另一个启动时间不同的进程占用。`ps` 读取失败按未知处理，返回 false。
3. worker 是自己进程组的组长（pgid == pid），且没有未完成的 spawn。
4. worker 自己的进程组已经没有成员。这个组没有组长了，无法确认里面的进程就是记录中的那些，所以只等待、从不 kill；`closedAt` 也不能跳过这一步。
5. 对 `commands`：不存在满足以下全部条件的进程：`comm` 等于该命令的程序路径、ppid 为 1、自身是组长、启动时间落在 [宣告时间, 最后心跳 + 4 s] 内。这一步同样只等待，从不 kill。
6. 对每个 `group`：
   - 组已空，则通过；
   - 组还在，且组长就是记录中的进程（启动时间落在 spawn 窗口内，按 ps 的整秒精度计算），则依次发 SIGTERM、SIGKILL，并确认组已消失；
   - 组长是窗口之后才启动的进程，说明原来的组已经结束，pid 被重新分配，按已结束处理；
   - 其余情况一律返回 false，且不发信号：组长不在但还有成员、组长早于窗口启动、`kill(-pgid,0)` 返回 ESRCH/EPERM 以外的错误。

### 发现：A1 的命令运行在各自的进程组

A1 的 `createCommandRunner` 以 `detached` 方式运行每条 2ndscreen 命令，不经过 LineProcessSpawner，因此 worker 无法知道这些命令的 pid。在不修改 A1 的前提下，采用上面第 5 条的“宣告 + 心跳 + 只等待”方案。更好的做法是给 A1 的 `createCommandRunner` 增加一个可选的 `onSpawn(pid)` 钩子，这样这些命令也能获得与 group 一样精确的身份。是否修改由协调者和 A1 的负责人决定。

### 打包与安装

- `scripts/fetch-node.sh`：下载 Node 22.23.2 的 darwin-arm64 或 x64 tar.gz，按 SHA-256 校验，并确认 `--version` 与预期一致。
- `scripts/install-task-runtime.sh [DEST]`：
  - 用这个 Node 自带的 npm 执行 `npm ci`，PATH 只包含该 Node 和系统目录；
  - 用 `build.mjs` 构建到临时目录；
  - 复制 `bin/node` 和 Node 的 LICENSE；
  - 用该 Node 运行 `main.mjs --help`，通过后才替换 DEST。
- 产物中只剩 `node:*` 内置模块的 import，包括 A4 引用的 agents/boss 解析器；不依赖 node_modules、npx 或当前工作目录。
- `bundle-app.sh`：
  - Runtime 装在 `Contents/Resources/task-runtime`，`bin/node` 保留 Node 官方签名，单独执行一次 `codesign --verify --strict`；
  - 同一构建的 CLI 放在 `Contents/Resources/bin/2ndscreen`，以标识 `….cli` 签名；
  - 实测 `codesign --verify --strict --deep` 通过。
  - TaskCommand 原有的查找逻辑（向上 4 层找到 .app）能从这个位置及其符号链接找到 Runtime。

### 旧 BOSS 助手的共享租约（agents/boss）

- `lease.ts`：`AppLease` 打开同一个账本，即 `$SECONDSCREEN_TASKS_DIR/tasks.db` 或默认路径，在 `com.zhipin.www:*` 上以 holder `legacy-assistant` 申请租约，TTL 60 s，每 20 s 续期。
  - 续期失败，或者本地时钟已进入到期前 15 s 的余量，就永久 fence，即使之后续期成功也不恢复。
  - 释放时只删除自己的那一行。
- `cli.ts`：每轮检查开始时取得租约，结束（包括出错）时释放，两轮之间 BOSS 留给任务使用。租约被任务占用时，本轮跳过并记录占用者。收到 SIGINT 或 SIGTERM 时释放租约。
- `boss.ts` 与 `setup.ts`：增加一个可选的 `fence` 钩子，`Boss.run`、`Setup.run` 和 `Setup.ensure` 在执行任何命令之前都会先检查它。

## 过程中的事故（如实记录）

1. 我误把 `build/2ndscreen.app/Contents/MacOS/2ndscreen`（菜单栏 App 本身，不是 CLI）当作 CLI 执行了两次。第一次以 `SECONDSCREEN_SOCKET` 指向临时路径，作为侧实例运行；第二次没有设置这个变量，以主实例身份运行约 2 分钟。两个进程都已结束。它在 `~/Library/Application Support/2ndscreen/` 留下一个没有进程监听的 `control.sock`，App 本身能处理这种残留。协调者在 `/tmp/2ndscreen-p0` 上的 P0 侧实例（49461）没有受到影响。这件事促成了把 CLI 放进 `Contents/Resources/bin` 的改动。
2. MCP 端到端用例第一次以 .app 内的 Runtime 运行时，Runtime 推导出了 app 路径，于是 worker 启动了本构建的侧实例（`/tmp/a7-mcp-…/none.sock`），并创建了 profile 屏幕。当时机器上的 BOSS（协调者此前启动的 pid 64054）不在这个屏幕上；适配器按规则拒绝接管（`not handed over; pass takeOver`），任务暂停后被取消，没有对 BOSS 执行任何动作。屏幕随 worker 退出而销毁，侧实例也已由我结束。之后两个测试都显式设置 `SECONDSCREEN_APP` 指向一个不存在的 .app，复测中没有再启动侧实例。

## 未验证项与已知限制

- 没有在真实桌面和真实 BOSS 上联调。任务入口到 A1 Session、A4 workflow、A5 Bridge 的真实链路由协调者验收；目前只确认了“没有桌面时如实进入等待”和“不接管别人的 BOSS”。
- 种子流程不导入，`inspect-procedure` 只能查看账本中已学到的流程。
- 计划第十一节提到的 MCP 任务资源链接没有实现，因为部分 MCP 客户端可能不认识 `resource_link` 内容类型。目前 status 返回 `outputPath`。
- 崩溃之后：
  - 只要 worker 自己的进程组还有成员、某个已记录的组只剩无组长的成员、或者还有正在执行的命令没有结束，任务就保持未决，并且阻塞整个队列（A6 的设计，一个应用同时只运行一个任务）；
  - 卡死的 2ndscreen 命令不会被杀，需要等它自己结束或由人处理；
  - 不是以独立进程组启动的 worker（例如手工在前台运行 `node worker.mjs`）崩溃后，它的任务永远无法自动解除，worker 启动时会在日志中写明这一点。
- 对 A1 命令的匹配条件（程序路径、ppid 1、独立进程组、时间窗）只用于等待，不用于 kill。如果时间窗内恰好有一个同路径的孤儿进程，只会让等待变长，不会误杀。
- 只测试了 arm64。x64 的 Node 已固定了 sha256，但没有实际运行过。
