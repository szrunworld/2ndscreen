## 设计

### 进程模型

- **CLI**（main.mjs）：每条命令打开账本，建一个 `claim:false` 的 daemon，只做一次控制调用，输出一行 JSON 后退出。`run` 和 `resume` 返回前调用 `ensureWorker`。如果 worker 起不来，会报错并在 details 中带上 taskId，说明任务已经记录。帮助信息和参数错误不会打开任何文件。
- **worker**（worker.mjs）：由 A6 的 `spawnDetachedWorker` 启动，是新进程组的组长，不继承 stdio，日志写入 `tasks/worker.log`。CLI 退出后它继续运行。以下情况会退出：
  - 收到 SIGTERM、SIGINT 或 SIGHUP，退出前由 daemon.shutdown 把运行中的任务转为 paused；
  - 空闲 10 分钟（`SECONDSCREEN_WORKER_IDLE_MS` 可调）；
  - 连续 35 秒拿不到 daemon 租约，说明它是重复实例，退出前不做任何动作。

  离开前它会关闭账本再重新检查一遍：如果有在它看完之后才排队的任务，就先拉起下一个 worker。
- **启动去重**：并发的 CLI 通过一个短租约 `2ndscreen.task-spawn:*` 轮流执行。轮到的 CLI 用 A6 的 `ensureDaemon` 等待 worker 真正持有 daemon 租约，后面的 CLI 再看时就会发现它。实测 6 个并发 CLI 只启动了 1 个 worker。
- **崩溃之后**：daemon 租约在到期前仍登记着已死的 worker。只有当租约持有者的进程确定已不存在（`kill(pid,0)` 返回 ESRCH）时，CLI 才启动一个候补 worker；进程是否存在无法判断，或者已经有活着的 worker 记录时，都不启动。候补只有在它自己的进程记录显示正在运行之后才算启动成功；如果它没有起来，CLI 会如实报错，错误中带 taskId 和日志路径。候补在旧租约到期后接管任务，任务交给 A6 的孤儿处理流程。
- **启动失败**：`startWorker` 装配中途失败时，会依次释放已经拿到的 vision、心跳、进程记录、账本和截图目录。

### 账号（显式绑定，不猜测）

- `run … --account KEY`：调用 A6 的 `submit(skillId, input, { account: { platform:'boss', accountKey: KEY, binding:'explicit' } })`，在 `task_published` 之前写入账号。
- `bind-account TASK_ID KEY`：调用 A6 的 `bindAccount`，只用于 paused 或 waiting_user 且尚未绑定账号的任务，已绑定的 key 不会被改。
- KEY 必须匹配 `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`，不能含 `:` 或 `/`。如果 control 没有 `bindAccount` 方法，返回 `capability_missing`，不会悄悄丢掉用户给的账号。
- 没有 `--account` 时 CLI 不编造账号，任务进入 `waiting_user / account_changed`。没有提供全局账号配置：配置文件过期会在用户换号后把错误的账号静默标成 explicit。

### 进程记录与退出核验（actors.ts）

记录文件为 `tasks/actors/<pid>-<startMs>.json`，0600，原子写入并 fsync，内容如下：

- worker 的 pid、pgid，以及由 A6 的 `processStartTime` 读到的启动时间。启动时间与 A6 写进 `WorkerRecord.processStartedAt` 的值来源相同，按完全相等比较。
- `pendingSpawns`：spawn 之前先写 +1，spawn 返回后在同一次写入里减 1 并加入该组。
- `groups`：LineProcess 子进程组，含 `spawnedAfterMs`、`spawnedBeforeMs`（spawn 前后的两次时钟读数）。
- `commands`：已宣告、但还没有收到 spawn 报告的 A1 命令（见下文“A1 命令的进程组”）。
- 运行期间每 2 秒刷新一次 mtime，作为心跳。
- 只有在所有组和命令都已确认结束时，才在退出时写 `closedAt`。

`verifyWorkerStopped` 只在以下条件全部成立时返回 stopped:true：

1. 不是 legacy 记录，且有 `processStartedAt`；能找到与 pid 和启动时间完全匹配的记录，记录格式合法（pid、pgid 大于 1，pending ≥ 0）。
2. worker 已不在运行：pid 不存在，或已被另一个启动时间不同的进程占用。`ps` 读取失败按未知处理，返回 false。
3. worker 是自己进程组的组长（pgid == pid），且没有未完成的 spawn。
4. worker 自己的进程组已经没有成员。这个组没有组长了，无法确认里面的进程就是记录中的那些，所以只等待、从不 kill；`closedAt` 也不能跳过这一步。
5. 记录里没有残留的 `commands`。只要有已宣告但没有 spawn 报告的命令，它的 pid 就无法确定，直接返回 false，不再按进程列表推测。
6. 对每个 `group`：
   - 组已空，则通过；
   - 组还在，且组长就是记录中的进程（启动时间落在 spawn 窗口内，按 ps 的整秒精度计算），则依次发 SIGTERM、SIGKILL，并确认组已消失；
   - 组长是窗口之后才启动的进程，说明原来的组已经结束，pid 被重新分配，按已结束处理；
   - 其余情况一律返回 false，且不发信号：组长不在但还有成员、组长早于窗口启动、`kill(-pgid,0)` 返回 ESRCH/EPERM 以外的错误。

### A1 命令的进程组

A1 的 `createCommandRunner` 以 `detached` 方式运行每条 2ndscreen 命令，每条命令自成一个进程组，不经过 LineProcessSpawner。我最初用进程列表推测崩溃后残留的命令，协调者判定这不足以证明，于是改为以下做法：

1. 我提出接口，协调者批准，由 A4 实现（161f492，已并入集成分支）：`createCommandRunner({ onSpawn, onSettled, now })`。onSpawn 在 runner 调用内同步执行，报告 pid 和 spawn 前后两次时钟读数。
2. `wrapRunner` 在调用 runner 之前先把命令写入记录（宣告）。`commandHooks().onSpawn` 先核对报告与宣告是否一致（同一程序、pid 大于 1、时间窗合法且不早于宣告），再在同一次写入中删除宣告、加入这个确切的进程组。
3. 报告与宣告不一致或写入失败时：记录标为 broken，宣告保留，之后不再启动任何子进程；onSpawn 抛出异常，A4 的 runner 随即杀掉该进程组并以 io 拒绝。
4. 只有在钩子已接上、runner 已结束、且没有收到任何 spawn 报告（说明进程没有启动）时，宣告才会被直接清除。
5. `onSettled` 之后，进程组一直留在记录里，直到组内没有任何进程为止。

### MCP 任务资源（后续任务 task_d299292fe8e9）

按计划第十一节补上任务资源链接，只修改 Sources/ScreenCLI/MCPServer.swift 以及测试和文档。

- `initialize` 声明 `resources` 能力，并记住协商的协议版本。
- `task_*` 调用成功（退出码 0、`ok:true`）后，在原有的文本结果后面追加两条 `resource_link`：`2ndscreen://tasks/<id>`（状态报告）和 `2ndscreen://tasks/<id>/artifacts`（产物索引），`mimeType` 均为 `application/json`。taskId 的来源：
  - `task_run` 取结果中的 `taskId`；
  - `task_status` 取 `task.id`；
  - pause、resume、cancel、bind_account 取返回记录的 `id`；
  - `task_artifacts` 取传入的参数。

  取到的 ID 还要再按 Runtime 的 ID 规则校验一次。失败的调用和 `task_inspect_procedure` 不附链接。
- 协议版本早于 2025-06-18 时不发 `resource_link`，改为追加一行文本 `resources: <两个 URI>`。

- 读取时执行与工具相同的 `task status ID` 或 `task artifacts ID`，返回 CLI 结果中的 `result`，类型 `application/json`。
  - 账本里没有这个任务时返回 -32002（MCP 的资源不存在），`data` 中带 Runtime 原始的 `not_found` 错误；
  - 其他错误返回 -32603，同样带上原始错误。
  - 不读取任何文件，也没有写操作。
- `resources/templates/list` 给出这两个 URI 模板；`resources/list` 返回空列表，因为任务不做枚举。

### 旧 BOSS 助手的共享租约（agents/boss）

- `lease.ts`：`AppLease` 打开同一个账本，即 `$SECONDSCREEN_TASKS_DIR/tasks.db` 或默认路径，在 `com.zhipin.www:*` 上以 holder `legacy-assistant` 申请租约，TTL 60 s，每 20 s 续期。
  - 续期失败，或者本地时钟已进入到期前 15 s 的余量，就永久 fence，即使之后续期成功也不恢复。
  - 释放时只删除自己的那一行。
- `cli.ts`：每轮检查开始时取得租约，结束（包括出错）时释放，两轮之间 BOSS 留给任务使用。租约被任务占用时，本轮跳过并记录占用者。收到 SIGINT 或 SIGTERM 时释放租约。
- `boss.ts` 与 `setup.ts`：增加一个可选的 `fence` 钩子，`Boss.run`、`Setup.run` 和 `Setup.ensure` 在执行任何命令之前都会先检查它。

  - 以下情况都不判为已停止：legacy 记录、没有启动时间、记录内容与文件名不符、记录格式错误、worker 仍在运行（包括 SIGSTOP 状态）、ps 读取失败、共享进程组、有未完成的 spawn、自身进程组非空或无法读取（即使有 closedAt）、组长已不在、组长早于 spawn 窗口启动、组无法读取。
  - 只有记录中的组长会被停止；组长晚于窗口启动时视为已结束。
  - 有未报告的命令时，无论进程列表如何，都判为未证明。
  - 有 spawn 报告时，宣告在同一次写入中变成确切的进程组，并保留到组内没有进程为止。
  - 没有接钩子时宣告一直保留；接了钩子、且确实没有 spawn 时才会清除。
  - spawn 报告写入失败（之后写入又恢复）时：宣告保留，记录标为 broken，后续 spawn 被拒绝，核验结果为 false。
  - spawn 报告的程序、pid 或时间窗与宣告不符，或者在宣告之外收到报告时，都会被拒绝。
  - 真实进程用例：SIGSTOP 的 worker 会阻塞核验；SIGKILL 之后，它遗留的分离辅助进程组被停止并确认已消失。

## 未验证项与已知限制

- 没有在真实桌面和真实 BOSS 上联调。任务入口到 A1 Session、A4 workflow、A5 Bridge 的真实链路由协调者验收；目前只确认了“没有桌面时如实进入等待”和“不接管别人的 BOSS”。
- 种子流程不导入，`inspect-procedure` 只能查看账本中已学到的流程。
- 崩溃之后，以下任一情况都会让任务保持未决，并按 A6 的设计阻塞整个队列（一个应用同时只运行一个任务）。目前没有手工解除的命令。
  - worker 自己的进程组还有成员；
  - 某个已记录的组只剩没有组长的成员；
  - 有已宣告但未报告 spawn 的命令；
  - 记录已被标为 broken；
  - worker 不是以独立进程组启动的（例如手工在前台运行 `node worker.mjs`），worker 启动时会在日志中写明这一点。
- 只测试了 arm64。x64 的 Node 已固定了 sha256，但没有实际运行过。
- 签名：`Contents/Resources/bin/2ndscreen` 使用本地自签名证书和标识 `io.github.szrunworld.2ndscreen.cli`，没有核实它对 TCC 权限的影响。CLI 本身通过 socket 让 App 执行动作，按设计不需要额外权限。
- 旧助手：
  - 交互式询问“是否发送”期间一直持有租约，任务需要等待；
  - 租约只在每条命令开始前检查，租约丢失时已经发出的那条命令会执行完；
  - 旧助手调用 `2ndscreen` 时没有设置超时，这一点保持原样。
- Node 22 的 `node:sqlite` 会输出 ExperimentalWarning，CLI 和 worker 通过 `--disable-warning=ExperimentalWarning` 屏蔽。
