## 实现要点

### 账本 store.ts

- 内置 `node:sqlite`（`DatabaseSync`）。文件库启用 WAL、`synchronous=FULL`、外键；显式 `PRAGMA busy_timeout=5000`（构造函数的 `timeout` 选项晚于 Node 22.13）。
- 迁移用 `PRAGMA user_version`：v1 建表（tasks、checkpoints、work_items、artifacts、events、leases、procedures），v2 加索引。旧版本先 `VACUUM INTO` 备份（文件名唯一）；在 IMMEDIATE 事务内重新读版本后才执行迁移，多个进程同时打开同一文件只迁移一次，后到者删除自己多余的备份。拒绝更高版本（`conflict`），也拒绝无版本号却已有表的外来库。
- 切换 WAL 不走 busy handler，并发首开会立刻报 `database is locked`；已改为“已是 WAL 就跳过，否则有界退避重试”。
- 所有“读-检查-写”在 `BEGIN IMMEDIATE` 事务内。SQLite 错误映射：FULL→`storage_full`，约束→`conflict`，BUSY→`io`（`details.busy`）。
- `transitionTask`：按 `canTransitionTask` 和可选 `from` 校验，非法抛 `conflict`。**补充约定**：`to` 等于当前非终态时只应用 patch（如 running 中切换 phase）；进入 `waiting_user` 必须带 waitReason，回到 running 或终态时清除。
- 账号绑定：`upsertWorkItem` 要求任务已绑定账号（`transitionTask(..., { account })`），且 `identity.accountKey` 与之相同；已有候选人后不允许换成其他 accountKey。
- `upsertWorkItem` 按 `candidateDedupeKey` 在任务内幂等：已知候选人保留原 id、状态和身份，只刷新与快照绑定的 ref。`candidateId`（目录名）在任务内唯一，不同去重键复用同一 candidateId 抛 `conflict`。
- `transitionWorkItem` 按契约迁移表执行；进入 processing 时 attempt+1。`committed` 只能经由 `commitItem` 进入。
- `commitItem` 在一个事务内完成：item 必须是 validated；每条记录必须属于该 item，路径必须在 `candidates/<该 item 的 candidateId>/` 下且每段通过 `safePathSegment`；`artifactRecordProblems` 校验记录自洽，伪造的 complete 记录会被拒绝，具体情形：
  - 大小或哈希与 validation 不符；
  - `sizeStable` 不为 true，或带有问题项；
  - 类型与 kind 不匹配；
  - captured_image 没有完整的采集证据；
  - PDF 没有解析出的页数。

  随后按 `isCountable` 决定 committed 或 failed（产物保留为诊断），同一事务写入事件，并在计数时更新检查点的 lastCommittedItemId。已 committed 的 item 用同样记录重复提交是幂等的，用不同记录提交抛 `conflict`；任一记录冲突整体回滚。
- `counts` 实时由 work_items 计算：browsed = attempt>0 或已离开 discovered；diagnostic = 有产物但未 committed 的 item 数。
- 租约：检查与插入在同一事务；与任何未过期且 `leaseScopesOverlap` 的租约冲突即抛 `lease_held`（含持有者详情）；过期的重叠租约被替换；过期租约不能续期（`conflict`），需重新申请；release 幂等。
- 流程：插入前做结构校验（`validateProcedure`，external-submit 是否允许属于引擎策略）；同一 (key, version) 或 id 重复抛 `conflict`；`updateProcedureState` 只改 status/counters/updatedAt，并对合并后的流程再跑一次 `validateProcedure`，`successItemIds` 必须是互不重复的非空 id，且数量不超过 successes。

### 产物 artifacts.ts

- 根目录为 `<outputDir>/<taskId>`（taskId 须通过 `safePathSegment`；outputDir 可以是符号链接，任务目录本身不可以）。每次尝试新建 `.staging/<itemId>.<attempt>/`（`mkdir` 非递归，名称不会复用），并写入 `.attempt.json`（pid、itemId）。
- `validate` 先确认路径：路径必须是该 item 自己 staging 目录下的普通文件，路径中不得有符号链接（realpath 必须与逻辑路径一致），不得是隐藏段或其他 item 的目录，文件不得有其他硬链接，否则抛 `invalid_input`。之后做以下检查：
  - 两次采样相隔 300 ms，大小与 mtime 不变；
  - 无临时下载后缀；
  - 按字节判定类型并实际解码；
  - 扩展名与内容不符记为问题；
  - 计算 sha256；
  - 解码期间文件变化记为问题。
- 解码方式：
  - **PNG**：逐块校验 CRC；按 IHDR（含 Adam7）先算出解压后应有的字节数，有上限，在分配内存之前检查；再以 `maxOutputLength` 解压 IDAT，必须正好等于该长度，并检查每行的滤波字节。
  - **DOCX**：解析中央目录与本地头，按声明大小有界解压 `[Content_Types].xml` 与 `word/document.xml` 并校验 CRC；再检查 XML 结构良好（不接受 DTD），并要求根元素为 document、其下有 body。
  - **PDF**：通过系统自带 `/usr/bin/osascript -l JavaScript` 调用 PDFKit，页数取自页面树（孤立的 /Page 对象不算页）；同时要求文件末尾有 `%%EOF`。
  - **JPEG**：要求有 EOI 标记，并经 ImageIO 完整绘制解码。
  - 旧版 `.doc`、非 macOS 平台、解码器缺失、超时或被取消：一律失败关闭，记为问题。
- 解码器 `MediaInspector` 可注入，默认使用 macOS 实现：单次 20 s 上限，取消或超时时 SIGKILL，并且等子进程退出后才返回。
- `archive`：拒绝不安全的 candidateId；非 diagnostic 的文件存在问题时拒绝归档；重新计算哈希，与 validation 不符抛 `conflict`。目标目录逐级 `lstat`/`realpath`，拒绝符号链接逃逸。完整性判定：original/resume_text/metadata 为 complete；captured_image 按 `captureCompleteness`，无证据为 unverified；captured_page 与 diagnostic 为 unverified。
  - 命名：original 用 `<sha12>.<ext>`（内容寻址，同一候选人的新版简历不会覆盖旧版）；captured_image 用 `captured/resume.png`，同名不同内容时用 `resume-<sha12>.png`；页面图保留安全的原 stem；候选人姓名不进入路径。
  - 写入顺序：先 fsync 源文件，然后原子写日志 `.journal/<artifactId>.json`，再 `link()` 到目标（原子且不覆盖已有文件；不支持硬链接的文件系统退回为“检查后 rename”），最后删除 staging 文件，staging 目录空了就一并删除。
  - artifact id 由（task、item、kind、路径、哈希、完整性）确定，重试归档相同内容会得到同一条记录，提交时自然幂等。
- `reconcile`（启动时、持有租约、尚无新尝试时调用）：
  1. 账本中缺失或内容已变的文件：列入 `invalidated` 并写 `artifact_missing` 事件。处于 acquired/validated 的 item 退回 processing；committed 保持终态不变。
  2. 日志中“已归档未入库”的记录：哈希核对通过，且 candidateId/accountKey/dedupeKey 与 item 一致，才经合法迁移（必要时经 processing→acquired→validated）调用 `commitItem` 补入，由 `isCountable` 判定是否计数，部分采集补入后依旧不计数。绑定不符或 item 已终态时不补入，只写事件。日志存在但文件不存在：删除该日志。
  3. 残留 staging：已死进程留下的移入 `.quarantine/` 供诊断，空目录直接删除；本进程任一 ArtifactStore 正在使用的、其他存活进程的、无标记的、符号链接的条目都不动，只写 `staging_skipped` 事件。
- `writeIndex`：原子写出 manifest.json、index.csv（UTF-8 BOM，页面文字中的公式前缀已中和）、failures.json，内容可完全由账本重建（同一时钟下逐字节一致），不含绝对路径。每个产物都重新核对磁盘状态（present/missing/changed）。`ledgerCounts` 是账本的历史计数；`delivered` 只统计 committed 且现有文件仍可计数的 item。failures 区分以下四类：
  - `saved_not_counted`：有产物但不计数，如部分采集；
  - `no_artifact`：没有产物，如导航失败；
  - `committed_evidence_missing`：已 committed 但证据缺失；
  - `artifact_damaged`：已交付但部分产物缺失或变化。
- `pickStagedFile(staging)`：staging 中只有一个已完成文件时返回它，零个或多个都抛 `conflict`，从不“取最新文件”。

## 测试命令与结果

在 `packages/task-runtime/` 下：

```
npm ci
npm run typecheck        # tsc --noEmit，通过；另用 --noUnusedLocals --noUnusedParameters 检查，无告警
npm test                 # tsx --test tests/*.test.ts
# tests 81  pass 81  fail 0   （含 A0 的 31 个契约测试；连续运行 3 次均无失败）
```

关键用例（均使用临时目录与合成夹具）：

- **真实崩溃**：子进程在 `rename` 前、后分别 SIGKILL。rename 前崩溃：staging 进隔离区，账本不变，item 可以重试。rename 后、提交前崩溃：重启后对账补入且只补一次；再次对账为空，磁盘上只有一份文件。
- **并发迁移**：6 个进程同时打开新库或 v1 库，全部成功，只迁移一次、只留一份备份。把迁移改回“事务外读版本”后，该测试稳定失败，说明测试确实能捕获这个问题。
- **重复与身份**：去重幂等、平台 ID 合并；candidateId 冲突、跨账号、未绑定账号、提交时目录归属错误或路径穿越，都被拒绝；重启后重新发现候选人不会重开已 committed 的 item。
- **拒绝伪造的 complete 记录**（9 种）：无采集证据或证据仅为部分、文件不稳定、哈希不符、大小不符、HTML 冒充图片、缺类型、带问题项、页面图声称 complete。诊断产物仍可保存且不计数。
- **部分采集**：保存后 item 为 failed，`diagnostic=1`，manifest 中 `delivered=0`；导航失败的 item 与之区分为 `no_artifact`。committed 后返回列表失败不会撤销 committed。
- **文件缺失或被篡改**：committed 保持，对账报告 `invalidated`，manifest 中 `delivered=0`，failures 中为 `committed_evidence_missing`。
- **解码**：
  - PNG：截断、CRC 错、垃圾 IDAT、像素不足、多余数据、坏滤波字节、缺 PLTE、声明超大尺寸（不分配内存即拒绝）都能检出，Adam7 可通过；
  - DOCX：XML 不良、无 body、CRC 错、超出声明大小、截断、缺 Content_Types 都能检出；
  - macOS 实测 PDFKit：合成 3 页 PDF 得 3 页，仅含 /Page 标记的伪造文件被拒，孤立页面只算 1 页，截断被拒；
  - macOS 实测 ImageIO：sips 生成的 JPEG 可解码，截断后补 EOI 的 JPEG 被拒；
  - 解码器缺失时失败关闭，original 不可归档；`.doc` 不可归档；取消和超时返回时子进程已退出。
- 路径安全：路径穿越、文件符号链接、目录符号链接、其他 item 的 staging、相对路径、候选人目录被预先替换为指向外部的符号链接，均被拒绝，外部目录无任何写入。
- 迁移：备份可读且保留原版本号；拒绝更高版本与外来库。租约：同一 bundle 的任意 scope 都冲突，两个连接（模拟两个进程）互相可见。流程版本不可改写，合并后状态仍须有效。

## 未验证项与已知限制

- 未接触真实 BOSS 或招聘账号；macOS 解码器只用合成文件验证过。真实 BOSS 附件与在线简历截图需在 P0/A4 的真实验收中复核。
- JPEG：libjpeg 会静默掩盖熵编码段中的损坏，中段损坏的 JPEG 仍可能解码成功；截断与头部损坏能检出。PNG 不依赖 ImageIO（实测 ImageIO 会把垃圾 IDAT 报告为 complete）。
- PDF 依赖 macOS 自带的 PDFKit（通过 osascript），其他平台一律失败关闭；PDFKit 对修复过的结构较宽容，因此额外要求有 `%%EOF`。不支持加密 PDF（失败关闭）、ZIP64 DOCX、旧版 .doc。
- `writeIndex` 与 `reconcile` 会对所有已入库文件重新计算哈希，产物很多时有 IO 开销（单个文件上限 200 MB）。
- `.quarantine/` 不会自动清理，需由后续清理策略（T17）处理。
- 同一进程内“正在使用的 staging”按进程登记；进程 pid 被复用时，残留目录会被保守地保留而不是隔离。

## 接入说明（A6/A7）

- **构造**：`openTaskStore({ path: defaultTaskDbPath() })`；`createArtifactStore({ outputDir: input.outputDir, taskId: task.id })`。`inspector` 是协调者批准的附加可选项，默认即 macOS 实现，测试可注入替身。
- **账号绑定**：准备阶段识别出账号后，先 `transitionTask(id, 'running', { account })`，再 `upsertWorkItem`。
- **归档顺序**：`stage` → acquire → `validate` → item 迁到 validated → `archive` → `commitItem` → `writeIndex`。validate 有问题时，可以把文件作为 `diagnostic` 归档留证，但它不会计数。下载落在 staging 时用 `pickStagedFile` 取文件，不要按时间挑选。
- **启动顺序**：先拿到租约，再调用 `reconcile`，之后才开始新的尝试。若 `invalidated` 中含 committed item 的产物，账本中的 committed 计数只代表历史；runner 判定成功前应以 manifest 的 `delivered`（或自行核对）为准，并决定是否另找候选人补足数量。
- **phase 更新**：以相同 status 调用 `transitionTask`（只应用 patch）。
- **事件**：store 自动写入 `task_status`、`item_status`、`item_committed`、`item_not_counted`；对账时写入 `artifact_missing`、`adoption_refused`、`journal_stale`、`staging_quarantined`、`staging_skipped`。
