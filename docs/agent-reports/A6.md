# A6 调度与恢复报告

## 目标

按 [task-runtime-contracts.md](../task-runtime-contracts.md) 的 A6 签名实现 `createTelemetry`、`createTaskRunner`、`createTaskDaemon`，把 A1–A5 的模块组合成一个持久的任务循环。要求包括：每位候选人开始前写检查点；成功数只算已验证并提交、且文件仍在磁盘上的项；来源耗尽时以 partial 结束；循环有上限；候选人与账号绑定；启动时先对账产物；`waiting_user / model_unavailable` 可以恢复；IO 锁与任务状态锁分开；status、pause、cancel 及时响应；取消被确认后不再有任何动作；用量持久化，未知 token 如实记为 unknown；worker 在调用它的 CLI 退出后继续运行，并安全接管孤儿任务；用租约保证只有一个 daemon 拥有任务。

## 行为要点

### 任务循环（runner.ts）

一次 `run(taskId, signal)` 的顺序如下：

1. 读取任务状态。终态，以及 paused、waiting_user（属于控制决定，只有 `TaskControl.resume` 能让它们回到 running）直接返回结果，不执行任何动作。`cancelling` 时本次运行还没有执行过任何动作，直接确认为 cancelled。queued 用 CAS 转为 running，并清掉旧的 error。
2. `analysis` 为 on（取任务输入，没有时取 spec 默认值）时，以 `failed / fatal_error` 结束，error 为 `capability_missing`。此时不打开会话。
3. `sessions.open` 获取租约和窗口。观察页面：登录页或验证码进入 waiting_user。
4. 账号绑定，按下面的顺序，绝不自行编造：
   - 任务记录已经绑定的账号；
   - 窗口中可读到的账号（A4 在 macOS 上始终返回 undefined）；
   - 可选依赖 `resolveAccount(task)` 返回的显式绑定；
   - 以上都没有时进入 `waiting_user / account_changed`，error 为“no BOSS account is bound”。

   可见账号与已绑定账号不同，同样进入 `account_changed`。accountKey 必须通过 `safePathSegment`，且不能含 `:`。原因是它会被拼进租约 scope `<bundle>:<key>`，含 `:` 会让 `leaseScopesOverlap` 判定不重叠，失去互斥。
5. 先对账，再开始新的尝试：`artifacts.reconcile`（拿到租约之后、任何新尝试之前）。仍处于 processing、acquired、validated 的项经合法迁移退回 discovered，之后从页面重新核对。随后 `writeIndex`，并持久化一次用量。
6. 运行 `select_source`。`job_ambiguous` 进入 waiting_user；`job_not_found` 以 failed 结束；`capability_missing`（original-only、recommend）进入 `waiting_user / capability_missing`。
7. 列表循环：enumerate → 逐个处理候选人 → advance_list。
   - `advance_list` 只有返回 `ok` 且 `reason === 'end_reached'`（或 listing 自身报告 endReached）时，才以 `partial / source_exhausted` 结束。
   - advance 连续失败 `maxStalledAdvances = 3` 次后转 paused，error 中写明“end is not confirmed”，不报告来源耗尽。
   - advance 总次数也有上限：max(100, 4 × (browseLimit 或 requestedCount × 5) + 已知项数)。

每位候选人的处理：

- 先检查四项限制：目标数、截止时间、浏览上限、预算。目标数按两步核对：账本中 committed 达到目标后，再逐个检查 committed 项的可计数文件是否仍在磁盘上、大小与 sha256 是否一致，然后才判定 succeeded。评审修正：这一步每次都实际读盘，不再缓存本次运行中刚提交的项，提交后被删除的文件不计数。
- 写检查点（unit 为 `open_candidate`）。之后每个单元开始前也会更新 unit。
- 运行 open_candidate 后，每次都调用 `workflow.identify`。不是 match，或 identity 的账号与任务账号不同时，标为 ambiguous 或跳过。`upsertWorkItem` 按身份去重。已终结的项（committed、unavailable、ambiguous，或已失败 2 次）直接跳过，不重新下载。
- 弱身份（confidence 为 weak）一律标为 ambiguous（`identity_weak`），不归档。总尝试次数超过 4 次的项标为 unavailable。
- 运行 open_resume。`request_dialog` 标为 unavailable，其他失败标为 failed，然后回到列表。
- 归档按固定顺序：`stage` → `acquireResume` → `verifyUnit('acquire_resume')`（评审修正：使用采集之后的新观察，persist_candidate 同样如此）→ acquired → 逐个 `validate` → validated → `archive`（未通过校验的文件以 diagnostic 归档留证）→ `commitItem` → 若 counted，再执行 `verifyUnit('persist_candidate')` → `writeIndex`。只有 `counted: true` 才更新 lastCommitted。
- 回到列表。失败时阶段转为 repairing 并重试一次，仍失败则停止。已 committed 的项保持不变。
- 单个候选人出现意外错误（io、not_found、conflict、timeout、snapshot_stale、window_lost）时，该项标为 failed 并继续；连续 3 次后停止。window_lost 会先 rebind。

每个单元的执行（契约“单元执行顺序”）：

1. 可学习的单元先 `engine.select`，有流程就 `replay`，再由 `verifyUnit` 复核。通过后 `recordOutcome(ok)`，并记一条 replay 遥测。
2. 没有流程时运行 `runScripted`，同样经 `verifyUnit` 复核。
   - 评审修正：回放失败后（页面不属于业务状态时），在调用模型之前保留确定性路径。先用一次新观察做 verify：单元其实已经完成的，不再发送任何输入（route 为 verified）。否则运行 `runScripted` 并 verify（route 为 scripted）。两条路径成功都会 `recordOutcome(fail)` 记录失败的流程，并写 `replay_fallback` 事件。都失败时，带着原来的回放失败结果（保留失败版本的信息）进入 recovery。
3. 失败后先看页面：登录页、验证码、索取确认框属于业务状态，直接返回原因，不交给模型，也不记为流程失败。workflow 报告的业务原因（`job_ambiguous`、`request_dialog`、`identity_mismatch` 等）同样不修复。
4. 不可学习的单元到这里就报告失败，永远不会走到模型。
5. 可学习的单元调用 `recovery.recover`，阶段相应切到 learning 或 repairing。失败版本的 `recordOutcome(fail)` 放在 recover 之后，所以 recovery 仍能通过 select 拿到该版本（用于 relocate 和 parentVersion）。
   - `repaired`：由 runner 调用一次 `learner.accept`，Bridge 已执行的动作不重发。
   - `model_unavailable`：进入 waiting_user，当前项退回 discovered。
   - 任务级预算耗尽：partial / budget_exhausted。
   - 单项预算耗尽：只有该项失败。

结束（finish）：

- 先 `session.close`，执行者在这里停下。之后才用 CAS 写入终态或等待状态。结束时按 `keepWindow` 释放窗口，等待和暂停时保留窗口。
- 被 signal 中止，或发现状态已被别人改动（pause、cancel）时，runner 不改写任务状态，该状态由触发方负责。
- 最后写 `run_finished`、用量和索引。

### 用量（telemetry.ts）

- `createTelemetry` 按事件计数。model_call 按 purpose 分别计数，token 用 `addTokens` 累计（unknown 具有传染性）。`unit` 事件只有 ok 时才计入 replayed 或 explored。
- runner 在每位候选人之后、每次结束时写一条 `usage` 事件。下次运行时读取最近一条作为基数，加上本次 recorder 的增量（`usageSince`：前后读数都是 unknown 且期间没有模型调用时增量为 0，其余涉及 unknown 的情况为 unknown）。elapsedMs 只累计实际运行的时间，墙钟预算按它判定。记录损坏时 token 按 unknown 处理，不写 0。
- `createTelemetryHub`：`forTask(taskId)` 传给 runner 的 `telemetry`；`shared` 传给 recovery 和 workflow，事件转发给当前任务。**ProcedureEngine 不要注入 telemetry**：replay 由 runner 计数，注入会重复计数。

### 控制与 worker（daemon.ts，评审修正后）

**租约只决定谁可以启动执行者，不证明旧执行者已经停下。** 租约过期可能只是旧 daemon 被挂起（SIGSTOP、休眠）；A5 的 Bridge 子进程在独立进程组中运行，父进程死亡后仍可能存活。因此本模块区分两件事：

- **租约过期**：只说明旧 owner 没有续期。新 daemon 可以因此成为 owner，但仅此而已，不据此改写任何任务状态。
- **已验证的退出**：只有两种正证据。
  1. `worker_finished{actorExited: true}`：由该 worker 自己的 daemon 在 `runner.run` resolve 之后写入。runner 只有在 `session.close` 成功后才会 resolve（session 关闭会等待进行中的动作，Bridge 在子进程组确认退出后才 resolve），所以这条记录可以作为证据。即使 daemon 已失去租约也会写，因为它是证据，不是决定。`runner.run` reject（例如关闭失败、清理失败）时写 `actorExited: false`，不能作为证据。
  2. `actor_exit_verified`：由注入的验证器（A7）给出，附带证据文本。

没有证据时：任务保持原状态（running 或 cancelling），pause 和 cancel 只作为意图记录；写一次 `actor_exit_unproven`（附原因）；**任何任务都不启动新的执行者**（同一 Skill 操作同一应用）。本模块不杀任何进程。

细节：

- **控制事件通道**：daemon 的生命周期事件写入 `itemId = CONTROL_ITEM ('~daemon')`（events.item_id 没有外键），每次全量读取这一小部分，不会因为其他事件很多而丢失。事件类型包括：`task_published`、`publication_missing`、`account_bound`、`worker_started{epoch, daemonId, ownerPid, processStartedAt, startedAt}`、`worker_finished{epoch, actorExited}`、`actor_exit_verified{epoch, source, evidence}`、`actor_exit_unproven{epoch, reason}`、`pause_requested`、`pause_applied`、`resume_requested`、`orphan_recovered`、`daemon_shutdown`。
- **续期失败**：只有租约确实失去（conflict、not_found，或本地计算已过期）才算失去所有权。账本暂时繁忙等瞬时错误不算，下一轮再续期。修正前，这类错误会中止 worker，并把任务错当成孤儿（全量测试在负载下暴露了这一点）。
- **worker 身份**：每次启动 worker 生成新的 epoch。记录的身份包括 daemonId（每个实例唯一）、ownerPid 和该进程的启动时间（ps lstart），这样 pid 被复用也不会被误认。
- **升级前的旧记录**：如果任务只有旧版写的、不带 item 的 `worker_started`（无 epoch、无启动时间），会被当作 `legacy: true` 的 worker，永远不会自动视为已退出，只能由验证器证明。这样旧的进行中任务不会被误判为没有执行者。
- **owner 的每轮轮询**：
  - 本进程有 worker：状态为 cancelling 时停止该 worker 并标为 cancel；状态不是 running，或有 pause 意图时，停止并标为 pause。
  - 本进程没有 worker：先判断是否已证明无执行者；未证明则调用验证器（每个 epoch 至少间隔 `verifyRetryMs`），仍未证明就阻塞调度。
  - 已证明无执行者：
    - cancelling → cancelled；
    - running 且有 pause 意图 → paused（写 `pause_applied`）；
    - running 且其 worker 已退出、之后没有 resume → paused，error 为 `lease_held`，并写 `orphan_recovered`。不报告成功，也不重跑；
    - running 且从未启动过 worker、或 resume 之后尚未启动 → 可以启动；
    - queued 且已发布 → 可以启动；
    - queued 但未发布 → 写一次 `publication_missing`，需要显式调用 `publish(taskId)`，不会被悄悄忽略。
  - 同一时刻只运行一个任务。有未证明的执行者时一律不启动新任务。
- **pause**：
  - 本进程有执行者：写 `pause_requested` 并中止执行者，执行者退出后由 settle 写 paused。
  - 已证明无执行者（从未启动，或已记录退出）：直接写 paused。
  - 其他情况：只写意图，由 owner 在证据出现后执行。

  回答前最多等待 `ackWaitMs`，绝不会在执行者停下之前声称 paused。
- **resume**：先写 `resume_requested`，再用 CAS 转为 running，这样 owner 不会把刚恢复的任务误判为孤儿。`runner.run` 不再自行恢复 paused 或 waiting_user 的任务（只有 `resume` 能做），避免与 pause 竞争。
- **cancel**：queued 直接 cancelled；其他状态先置 cancelling。本进程有执行者时，在执行者退出后确认；已证明无执行者时立即确认；否则保持 cancelling。不再用“临时拿到租约”或“本地没有 worker”来证明没有执行者。
- **账号**：`submit(skillId, input, { account })`，或 daemon 选项 `accountFor(skillId, input)`，在 `task_published` 之前写入账号，调度器只启动已发布的任务，所以第一次运行时就带着账号。`bindAccount` 只用于 paused 或 waiting_user 的任务，允许首次绑定，不允许更换已绑定的键。
- **状态锁与 IO 锁分开**：同前。每个任务一把进程内状态锁，只包住短事务；跨进程竞争由 CAS 处理；GUI 只属于 runner 的 session。
- **shutdown**：中止 worker；worker 退出后先写 `worker_finished`，再转 paused（写 `daemon_shutdown`）；最后释放租约。
- **启动钩子**：
  - `spawnDetachedWorker` 改为 async：收到 `spawn` 事件后 resolve；`error` 事件转为 `capability_missing` 并 reject，之后的错误被吞掉，不会让调用方崩溃。
  - `ensureDaemon(store, cmd, { readyTimeoutMs = 10000 })`：只有在租约被持有时才 resolve，并返回 `ownerPid` 和 `ownedBySpawned`（持有者是否就是所启动的进程或其进程组内的进程）。子进程先退出时立即以 io reject（带 code 和 signal）；超时以 timeout reject（details 中带 pid，进程保留不杀）。
  - `daemonOwnerPid(store)`、`daemonRunning(store)` 用于探测。
- **进程身份工具**（供验证器组合使用，自身不杀进程）：`processStartTime(pid)`；`processIdentity(pid, startedAt)` 返回 `'alive' | 'gone' | 'unknown'`。

### 验证器接口（A7 实现）

```ts
type WorkerRecord = { taskId; epoch; daemonId; ownerPid; processStartedAt?; startedAt; legacy?: true };
type ActorExitVerdict = { stopped: true; evidence: string } | { stopped: false; reason: string };
type ActorExitVerifier = (worker: WorkerRecord, ctx: { signal: AbortSignal }) => Promise<ActorExitVerdict>;
createTaskDaemon({ ..., verifyActorExit, verifyRetryMs });
```

只有 owner 会调用它，而且只针对“最新 worker 没有退出证据”的任务。只有给出非空 evidence 的 `stopped: true` 才被采纳；验证器抛错按 `stopped: false` 处理。A7 的计划（已与 A7 对齐）：worker 启动时写 actor 注册表（自身 pgid，以及每个 Bridge/vision 子进程组的 pgid 和启动时间）。验证器要求以下条件全部成立才返回 stopped：

- 进程身份检查结果为 gone；
- worker 的进程组为空；
- 每个登记的组为 gone，或者是启动时间一致的 alive——此时先 SIGTERM，再 SIGKILL，然后复核为 gone。

任何 unknown、注册表缺失或启动时间不一致，都返回 `stopped: false`。

## 给 A7 的装配建议

```ts
const store = await openTaskStore({ path: defaultTaskDbPath() });
const hub = createTelemetryHub();
const engine = createProcedureEngine({ repository: store });            // 不注入 telemetry
const learner = createLearner({ repository: store });
const recovery = createRecovery({ engine, learner, explorer, telemetry: hub.shared });
const workflow = createBossResumesWorkflow({ vision, telemetry: hub.shared });
const runner = createTaskRunner({ store, sessions, artifacts: (t) => createArtifactStore({ outputDir: t.input.outputDir, taskId: t.id }),
  engine, learner, recovery, workflow, spec, profile, telemetry: hub.forTask, resolveAccount /* 可选 */ });
// worker 进程：createTaskDaemon({ store, runner, specs, verifyActorExit, accountFor? })，SIGTERM → shutdown()
// CLI 进程：createTaskDaemon({ store, runner, specs, claim: false }) → submit(skillId, input, { account }) → ensureDaemon(store, { command, args }, { readyTimeoutMs }) → 退出
```

显式账号在 submit 时随任务一起写入，早于发布，因此不存在“先 submit 再 bindAccount”的竞争。没有账号的任务会停在 `waiting_user / account_changed`，之后用 `bindAccount` 加 `resume` 继续。账号确定之后，store 拒绝绑定到另一个已有候选人的账号，因此不同账号的人不会被合并。

5. 动作进行中取消：runner 先关闭 session 再返回，之后没有任何动作。
6. 不完整采集只作为诊断保存，不计数；结果为 partial / source_exhausted。
7. 列表结束无法确认：有限次数后转 paused，不报告来源耗尽。
8. 弱身份标为 ambiguous；达到浏览上限时以 partial / browse_limit 结束。
9. 账号不一致或在登录页时进入 waiting_user，且没有任何动作。
10. 会话打不开：lease_held 转 paused，permission_missing 进入 waiting_user；resume 后清除旧 error。
11. 没有绑定账号时进入 waiting_user / account_changed；显式绑定后可以运行。
12. `analysis: on` 以 failed / capability_missing 结束。
13. 首次学习：usageContext 为 `ui/missing_procedure`，第二位候选人立即复用 trial。

1. submit 立即返回，owner 串行执行任务。非法输入、`analysis: on`、非法账号键都会被拒绝。未发布的 queued 任务会被记录 `publication_missing`，不会运行，`publish` 之后才会运行。

真实进程测试，都使用 detached worker，部分 worker 还带一个 detached 的 actor 子进程（独立进程组，模拟 Bridge）：

14. CLI 退出后，worker 独立完成任务，ensureDaemon 报告 `ownedBySpawned`。第二个 CLI 不再启动新 worker。SIGKILL worker 之后，没有验证器的 owner 保持任务 running；按身份核对的验证器证明退出后，任务才转为 paused，期间没有杀任何进程。
15. **旧 daemon 挂起（SIGSTOP）且 actor 仍在运行**：新 owner 在旧租约过期后接管，但任务保持 running，cancel 保持 cancelling，期间可以看到 actor 心跳仍在增长，新任务不会启动。SIGCONT 之后，旧 daemon 发现租约已失，停止 actor 并等待其退出，写下 `worker_finished{actorExited: true}`；新 owner 随后确认取消，此时 actor 的身份核对结果已是 gone，心跳停止，新任务这才开始运行。
16. **worker 被 SIGKILL，detached actor 存活**：没有验证器时任务保持 unresolved，actor 继续心跳；验证器核对 actor 的启动时间之后，只停止登记的那个进程组，任务转为 paused。
17. **清理失败**：actor 忽略 SIGTERM，worker 的 runner 因此 reject，记录 `actorExited: false`，cancel 不被确认。worker 关闭后，验证器核对身份、停止 actor，取消才被确认。

## 未验证项与已知限制

- 未与真实的 A1 Session、A4 workflow、A5 Bridge 在真实桌面上联调。runner 测试中的 Session、Workflow、Bridge 都是 fake。协调者告知 P0 真实模块运行目前卡在原生屏幕创建超时，本模块没有依据这个环境问题放宽任何判定。
- 没有可读账号时使用的等待原因借用了 `account_changed`，契约中没有专门的“需要绑定账号”原因；error 文本写明了需要显式绑定。如需新增 WaitReason，需要协调者修改契约。
- 孤儿任务只有在证明退出之后才转为 paused，之后需要显式 resume，不会自动重跑。没有配置验证器时，崩溃留下的孤儿会一直阻塞调度，直到 A7 的验证器给出证据。这是按要求有意采取的保守做法；升级前的旧记录同样如此。
- 验证器的正确性取决于 A7 的 actor 注册表是否完整（Bridge、vision 等每一个 detached 子进程组都要登记）。本模块只采纳验证器给出的证据，无法替它保证完整。
- 被 signal 中止的 runner 不改写状态。runner 单独使用（不经 daemon）时被中止，任务会留在 running；之后 daemon 会把它当作从未启动过 worker 的任务来启动。
- 进程身份基于 ps lstart，精度为 1 秒。刚被杀死、尚未被回收的僵尸进程会被判为 unknown，验证器下一轮重试即可（测试中也观察到了这种情况）。
- 评审修正期间，有一次全量运行中 A5 的 `agent-bridge.test.ts` “a last line cut off before its newline is not trusted” 失败（期望 'error'，实际 'timeout'），发生在负载较高时。这不是本模块的文件，没有修改，修正后连续 3 次全量运行均通过。
- submit 在 createTask 与 task_published 之间崩溃，会留下未发布的 queued 任务，并带有 `publication_missing` 记录，需要 publish 或 cancel。
- 每次提交后调用一次 `writeIndex`（契约第 6 步）。它会对全部产物重新计算哈希，候选人很多时开销为 O(n²)。
- daemon 一次只运行一个任务（同一 runner 对应同一应用）。不同应用的并发不在本次范围内。
- 跨进程 pause 依赖 owner 轮询（默认 500 ms），在“两秒内受理”的目标之内；同进程的 pause 立即中止执行者。
- 用量的 elapsedMs 只累计实际运行的时间，paused 或 waiting 期间的时间不计入墙钟预算。
